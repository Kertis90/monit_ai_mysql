# MySQL AI Monitoring — полный стек с WebSocket-чатом

Мониторинг неограниченного количества MySQL-кластеров (primary + replica) с ИИ-анализом
алертов и чатом на русском языке. LLM — **удалённая** (ваш OpenAI-совместимый API),
локально ничего не разворачивается.

mysqld_exporter  mysqld_exporter        (порт 9104)
node_exporter    node_exporter          (порт 9100)
   │                │                       │
   └────────────────┴───────────┬───────────┘
                                ▼
                       Prometheus :9090 ──► Grafana :3000
                                │
                       Alertmanager :9093
                                │ webhook
                                ▼
                     ┌─────────────────────┐
                     │  AI Agent :5001      │
                     │  FastAPI + WebSocket │
                     │  /ws  — стрим-чат    │
                     │  /webhook — алерты   │
                     │  web/ — интерфейс    │
                     └──────────┬──────────┘
                                │ HTTPS + Bearer
                                ▼
                     Удалённая LLM (ваш API)
                     /v1/chat/completions
```

**Как работает чат.** Вы пишете «Вчера в Кемерово БД было плохо. Почему?».
Агент: (1) находит кластер `kemerovo` по слову «Кемерово» (включая падежи —
«в Кемерове» тоже сработает); (2) распознаёт «вчера» → загружает историю метрик
за 30 часов из Prometheus (min/avg/max + время пиков); (3) добавляет текущие
метрики; (4) отправляет всё в вашу LLM; (5) стримит ответ токен за токеном
в браузер через WebSocket.

## Что агент собирает при разборе

**Профиль нагрузки — то, что происходит сейчас.** `events_statements_summary_by_digest`
копит суммы с момента запуска сервера: на базе с аптаймом полгода топ по
`SUM_TIMER_WAIT` показывает средние за полгода, а запрос, положивший всё
минуту назад, может оказаться на двадцатой строке. Поэтому агент снимает два
среза с интервалом и вычитает — в разбор попадает то, что исполнялось именно
в эти секунды. То же со счётчиками: `Innodb_rows_read` за всё время
бесполезен, прирост за окно — нет.

```bash
WORKLOAD_WINDOW_S="10"      # 5-60 с; на столько же задерживается ответ
```

Видно отношение просмотренных строк к отданным: тысяча просмотренных на одну
отданную — это и есть отсутствующий индекс, без всяких догадок.

**Порядок проверок — не список, а методика.** Документация Performance
Schema советует не гадать по отдельным показателям, а идти сверху вниз:
сначала «во что упёрлись» (классы ожиданий), потом конкретные запросы, потом
схема. Набор агента выстроен так же:

| Слой | Что смотрим | Откуда |
|---|---|---|
| 1. Во что упёрлись | классы ожиданий: диск, блокировки, сеть | `sys.wait_classes_global_by_latency` |
| 2. Какие запросы | тяжёлые, со сканами, с временными таблицами на диске, с сортировкой | `sys.statements_with_*`, `events_statements_summary_by_digest` |
| 3. Какие таблицы и файлы | что читают целиком, что греет диск | `sys.schema_tables_with_full_table_scans`, `table_io_waits_*`, `file_summary_*` |
| 4. Что мешает прямо сейчас | активные сессии, ожидания блокировок | `PROCESSLIST`, `sys.innodb_lock_waits` |
| 5. Схема и память | таблицы без первичного ключа, широкие ключи, лишние индексы, на что ушла память | `information_schema`, `sys.schema_unused_indexes`, `sys.memory_global_by_current_bytes` |

Две проверки схемы стоят отдельного слова, потому что их не видно ни в одной
метрике:

- **таблицы без первичного ключа.** При строчной репликации каждое изменение
  такой таблицы заставляет реплику перечитывать её целиком — это самая частая
  причина лага, которую ищут неделями;
- **нецелочисленный первичный ключ.** Первичный ключ InnoDB дописывается в
  каждый вторичный индекс, поэтому строковый ключ раздувает их все разом.

**Версии учитываются, а не игнорируются.** В парке живут и 5.6, и 5.7, и 8.x,
и MariaDB — а половина современных рецептов диагностики написана под схему
`sys`, которой на 5.6 нет вовсе. Агент спрашивает `VERSION()` (ответ помнит
час), разбирает номер и сборку и берёт только применимое:

| Сервер | Набор | Блокировки читаются из |
|---|---|---|
| MySQL 5.6 | 12 проверок, без `sys` | `information_schema.innodb_lock_waits` |
| MySQL 5.7 / 8.x, Percona | 19 проверок | `sys.innodb_lock_waits` |
| MariaDB 10.6+ | 19 проверок | `sys.innodb_lock_waits` |
| MariaDB до 10.6 | 12 проверок, без `sys` | `information_schema.innodb_lock_waits` |

Условие для запасного пути — «там, где нет `sys`», а не «до версии такой-то»:
`information_schema.innodb_lock_waits` Oracle убрал в 8.0, а MariaDB держит до
10.6, и правило по номеру версии здесь просто не существует.

Пропущенное не исчезает молча — отчёт заканчивается списком:

```
### Пропущено на этой версии — mysql 5.6.51
  Во что упирается сервер — нужна схема sys: она появилась в 5.7
  Запросы, читающие таблицы целиком — нужна схема sys: она появилась в 5.7
```

Если версию узнать не удалось (нет `db_user`, сервер не ответил), не
отсекается ничего: пусть лучше лишний запрос упадёт и пропустится как
необязательный, чем агент вырежет работающую проверку из-за незнания.

**Рядом — `SHOW FULL PROCESSLIST`.** У дайджеста есть неустранимый
недостаток: текст в нём нормализован — литералы заменены на `?`, а сама
строка обрезана по `performance_schema_max_digest_length`. Для вопроса «что
грузило базу за окно» это правильно (одинаковые запросы складываются в
один), но для «покажи мне этот запрос» не годится: по нему нельзя ни
повторить его, ни объяснить, почему он читает миллион строк именно сегодня.

Поэтому вместе со вторым срезом агент снимает список выполняемого прямо
сейчас — с полным текстом и настоящими значениями:

```
  Выполняется прямо сейчас (SHOW FULL PROCESSLIST):
    Соединений 412, из них спящих 409, работают 3.

  1. 42 с · billing@10.0.0.9 · база lanbilling · Sending data
       SELECT `uid`, `agrm_id`, `balance` FROM `agreements`
       WHERE `archive` = 0 AND `balance` < -100 ORDER BY `balance`
```

Спящие соединения отбрасываются — их обычно девять из десяти, — но их число
показывается: «соединений 412, из них 409 спят» само по себе диагноз.
Сортировка по времени выполнения: сверху то, что идёт дольше всех.

**Репликация: почему, а не только на сколько.** Лаг из метрик отвечает «на
сколько», состояние — «почему»: остановленный поток, ошибка применения с
номером, забитый relay log, непринятые GTID. Отставание на величину
запланированной задержки (`MASTER_DELAY`) отделено от реального — агент
показывает строку «сверх плана» и не поднимает тревогу из-за штатных двух
часов. Отдельно предупреждает, что `Seconds_Behind_Source` на простаивающем
источнике показывает 0 при реальном отставании.

Поддержаны оба набора имён колонок: MySQL 8.0.22 переименовал `Slave_*` в
`Replica_*`, и в одном кластере могут оказаться серверы разных версий.

**Чего собрать не удалось — сказано прямо.** Раньше недоступный по SSH сервер
или незаполненный `db_user` просто означали отсутствие блока, и модель
отвечала так же уверенно, как если бы видела всё. Теперь в контекст идёт
список пробелов, а в системной подсказке — правило: о том, чего не видел, не
судить и назвать в ответе, какой проверки не хватило. Отличить «проблемы нет»
от «не смотрел» стало возможно.

**База сравнения — медиана по неделям.** Раньше сравнивали с одной точкой
неделю назад. Если ровно тогда был сбой, праздник или разовая выгрузка, база
кривая: агент объявляет аномалией нормальную нагрузку или наоборот. Теперь
берётся медиана за несколько недель на тот же день недели и час — выбросы
отбрасываются, а суточный и недельный профиль сохраняется, и ночной бэкап
сравнивается с ночным бэкапом.

```bash
BASELINE_WEEKS="4"          # 1-12; недели опрашиваются параллельно
```

Недели за пределами хранения Prometheus просто не попадают в медиану, и в
блоке сравнения сказано, за сколько недель она посчитана.

**Помогло ли решение.** Записанное в инцидент решение подкладывается при
повторе как проверенное — хотя проверял его только тот, кто записал. Теперь
через заданное время агент сам смотрит, не повторилось ли событие, и
дописывает вывод:

```
почистили /var
[проверено через 15 мин: не повторялось — решение выглядит рабочим]
```

либо `ПОВТОРИЛОСЬ через 4 мин (записей: 3) — решение не помогло или устранило
следствие`. Повтор, случившийся до записи решения, за провал не считается.

```bash
FOLLOWUP_MINUTES="15"       # 5-60 мин
```

Проверки живут в памяти процесса, поэтому при запуске агент восстанавливает
пропущенные за время простоя.

**Инструменты модели.** К прежним добавились `get_workload` (профиль за окно)
и `get_replication` — модель может проверить гипотезу сама, а не гадать по
приложенному контексту.

## Доступ на серверы БД

Учётная запись и ключ задаются один раз в `config.env` и используются везде:
установка экспортёров, чтение логов, SSH-туннель к базе, проверка резервных
копий.

```bash
SSH_USER="monitor"
SSH_PORT="22"
SSH_KEY="/home/admin/.ssh/id_monitor"    # пусто — ключ по умолчанию
```

Путь к ключу необязателен: без него используется ключ учётки, из-под которой
идёт обращение.

**Ключ и учётка агента.** Здесь есть ловушка, из-за которой всё по SSH молча
переставало работать. Агент выполняется под служебной учёткой `aiagent`, а
ключ обычно лежит в домашнем каталоге администратора с правами `600` — и
прочитать его агент не может. Внешне это выглядело как «сервер не отвечает по
SSH», хотя сервер отвечал прекрасно.

`install_agent.sh` теперь проверяет доступность ключа этой учётке и, если
доступа нет, делает закрытую копию в `/opt/ai-alert-agent/.ssh/id_agent`
(владелец `aiagent`, права `600`) и подставляет её путь в окружение агента.
Права на исходный ключ при этом не меняются: раздавать доступ к ключу
администратора ради одной службы — плохой размен.

Юниту добавлен `Environment=HOME=/opt/ai-alert-agent`: у служебной учётки нет
домашнего каталога, а `ssh` без него не находит своих настроек и падает ещё
до подключения.

Если что-то не так, причина называется прямо — в интерфейсе, в самопроверке и
в логе:

```
SSH-ключ /home/admin/.ssh/id_monitor недоступен учётке, под которой работает
агент. Переустановите агента — он сделает читаемую копию.
```

`manage_cluster.sh install-exporters` берёт те же настройки и позволяет
переопределить их разово: `--user`, `--port`, `--key`.

## Знания о кластере и история изменений

**Известные особенности.** Агент в каждом разборе заново «открывал» плановые
вещи: всплеск в три часа ночи, растущую по расписанию таблицу, привычный для
старого железа iowait. Теперь это записывается один раз на странице кластера и
подмешивается в каждый разбор:

> Всплеск в 3:00 — это бэкап, останавливать не надо.
> Таблица `billing.charges` растёт из-за выгрузки и чистится по субботам.

В системной подсказке сказано прямо: не предлагать разбираться с тем, что
здесь названо нормой.

**Что менялось в настройках.** Самый частый вопрос при внезапной деградации —
«что вчера поменяли». Снимок отслеживаемых переменных снимается раз в сутки,
диф между снимками попадает и в отдельный отчёт, и в ленту событий рядом с
алертами:

```
[2026-09-14 03:15] max_connections на 10.1.0.1: было 500, стало 2000
```

Сравниваются соседние снимки, а не первый с последним: значение, изменённое и
возвращённое обратно, иначе потерялось бы — а это как раз самый интересный
случай.

**Лишние индексы.** Неиспользуемые диагностика показывала и раньше. Теперь
находятся дублирующие (тот же набор колонок в том же порядке) и избыточные —
индекс по `(a)` не нужен, когда есть `(a, b)`: он занимает место, обновляется
при каждой вставке и сбивает оптимизатор. Уникальные и первичные не трогаются
никогда: они держат ограничение целостности, а не только ускоряют выборку.
Для каждого выводится готовая команда удаления.

**Копии баз.** Свою базу агент бэкапит сам, а за копиями СУБД обычно не следит
никто. Проверяется возраст последней, её размер и то, не похудела ли она
против предыдущей — внезапно уменьшившийся дамп означает, что снятие
оборвалось. Каталог задаётся у кластера:

```json
"backup_dir": "/var/backups/mysql",
"backup_pattern": "*.gz",
"backup_max_age_hours": 26
```

Восстановимость этим не подтверждается — тестовое восстановление всё равно
делается руками. Но «копий нет уже неделю» будет замечено вовремя.

**Прогноз доходит до дежурного.** `manage_cluster.sh apply` генерирует правила
Prometheus из `predict_linear`: место кончится через трое суток — `critical`,
через две недели — `warning`, соединения упрутся в предел за неделю —
`warning`. Дальше обычный путь: Alertmanager, почта, смена. Прогноз, который
видит только открывший вкладку, до дежурного не доходит.

## Предупреждать, а не констатировать

**Запас по ресурсам.** «Занято 85%» описывает состояние, «хватит на трое
суток» — даёт время что-то сделать. Считается три вещи: когда кончится место
на дисках (остаток и производная по неделе), когда упрёмся в
`max_connections`, и сколько осталось до **переполнения автоинкрементов**.
Последнее в мониторинге почти никогда не настроено, потому что метрики для
него нет: `int` в большой таблице кончается внезапно и кладёт запись на часы,
хотя предсказуемо за месяцы.

**Разбор настроек MySQL.** То, что DBA делает руками раз в год: буферный пул
относительно ОЗУ, `innodb_flush_log_at_trx_commit` в паре с `sync_binlog`
(от них зависит, теряете ли вы подтверждённые транзакции при отключении
питания), размер журнала повторов, формат binlog и срок его хранения,
`table_open_cache` против фактического числа открытий, временные таблицы на
диске. Каждое замечание объясняет последствие и помечено, требует ли
перезапуска. На разумно настроенном сервере отчёт пустой — проверено.

**Что растёт.** Срез размеров таблиц раз в сутки, дальше — разница между
снимками: что растёт быстрее всех, где освободившееся место не вернулось
файловой системе, где нет первичного ключа (при построчной репликации это
превращает обновление сотни строк в полный проход).

**Тихие поломки.** Медианная база сравнения теперь проверяется по расписанию.
«Запросов вдвое меньше обычного для этого часа» не пересекает ни одного
порога — база здорова, отвалилось приложение. Такое отклонение заводится
обычным событием и всплывает уведомлением.

**Можно ли трогать.** Перед перезапуском, ALTER или снятием копии: долгие
транзакции, зависшие запросы, ожидание блокировок метаданных, состояние
реплик. Вердикт подсказывает, а не запрещает — решение за человеком.

**Самопроверка.** Prometheus, модель, SSH до каждого сервера, учётки баз,
каталог — по расписанию и вкладкой «Здоровье». Протухший ключ или отозванные
права `db_user` приходят событием, а не обнаруживаются в разгар аварии, когда
агента и зовут разбираться.

```bash
ANOMALY_ENABLED="true"      ANOMALY_INTERVAL_MIN="30"
SELFCHECK_ENABLED="true"    SELFCHECK_INTERVAL_MIN="60"
```

**Резервная копия базы агента.** История инцидентов с решениями копится
месяцами в одном файле:

```bash
./scripts/backup_agent.sh                 # в /var/backups/ai-agent
./scripts/backup_agent.sh --restore ФАЙЛ  # восстановить
15 3 * * * /opt/mysql-ai-monitoring/scripts/backup_agent.sh   # в cron
```

Копия снимается штатным `.backup`, а не `cp`: копировать файл SQLite во время
записи — верный способ получить битую базу. Хранилище в MySQL выгружается
`mysqldump --single-transaction`. При восстановлении прежняя база не
удаляется, а отодвигается — если копия окажется битой, есть куда вернуться.

## Вкладки интерфейса

| Вкладка | Что даёт |
|---|---|
| **Чат** | вопросы агенту, список разговоров, графики и оценка ответов |
| **Кластер** | всё, что агент собирает для разбора, — одним экраном |
| **Статус** | сводка по всем кластерам |
| **Алерты** | лента событий с разбором и действиями |
| **Логи** | slow-лог и логи ядра за период, с поиском по строке |
| **SQL** | читающие запросы с готовыми шаблонами и историей |
| **Поиск** | по своей переписке и по истории событий сразу |
| **Здоровье** | работает ли сам агент: Prometheus, модель, SSH, базы, каталог |
| **Доступы**, **Журнал** | для администраторов |

**Страница кластера.** Щелчок по кластеру слева открывает его экран: плитки
состояния с подсветкой (соединения под 80% — жёлтая, MySQL не отвечает —
красная), графики за выбранный период, события за сутки. Тяжёлое — профиль
нагрузки, состояние репликации, диагностический набор — грузится по кнопке:
у профиля окно в секундах, и ждать его при каждом открытии незачем.

**Вкладка доступна всегда.** Раньше она появлялась только после щелчка по
кластеру слева, и тот, кто об этом не знал, просто не находил раздел. Теперь
вкладка на месте с самого начала: без выбранного кластера она показывает
список — выбрать можно прямо там. Выбор запоминается в браузере, поэтому
перезагрузка открывает тот кластер, с которым работали.

**Период задаётся не только готовыми кнопками.** Кроме «за час / 3 часа /
12 часов / сутки» в списке есть «свой интервал…»: два поля «с» и «по». Разбирают
обычно конкретный случай — «вчера в 17:40 всё встало», — и смотреть надо вокруг
этого времени, а не последние сутки, внутри которых всплеск теряется.

Ограничение одно: не больше суток. Оно же живёт в `MAX_METRICS_HOURS`, так что
поднимается настройкой, если нужно.

Границы уходят на сервер **Unix-временем**, а не строкой с датой: кластеры
живут в разных городах, и «с 3:00» без уточнения, чьи это три часа, ничего не
значит. В поле человек видит своё местное время, дальше оно становится
однозначным.

Что проверяется до отправки, с объяснением прямо у полей:

| Что не так | Что написано |
|---|---|
| конец раньше начала | «Конец интервала раньше начала.» |
| интервал шире суток | «Интервал больше суток. Максимум — 24 ч.» |
| начало в будущем | «Начало в будущем — метрик оттуда ещё нет.» |

Сервер всё равно приводит границы к разумным (перевёрнутый интервал
разворачивает, будущее обрезает по «сейчас», слишком широкое окно сужает,
сохраняя свежий край) и **возвращает то, что применил**, — на экране
подписано ровно то, что показано: «Метрики 10.09 с 03:00 до 07:30». Тот же
интервал уходит и в печатный отчёт по кнопке «Выгрузить PDF».

**Сверху — ответ на вопрос «всё ли в порядке».** Полоса с вердиктом:
«Работает нормально» / «Есть на что посмотреть: реплика отстаёт» / «Требует
внимания: диск не успевает». Человек, открывший страницу, хочет узнать это
раньше, чем начнёт читать числа.

**Состояние одним рядом плиток.** У каждой — название, значение, полоса
заполнения для процентов и спарклайн за выбранный период. Тревожная плитка
подписана словом — «внимание», «критично», — а не только покрашена: цвет сам
по себе ничего не говорит тому, кто его не различает, и мало что новичку.

**Блоки диагностики — свёрнутые строки по группам.** Было тринадцать
одинаковых развёрнутых карточек: всё одного веса, и до нужной надо было
прокрутить пять экранов. Стало четыре группы — «Что происходит сейчас»,
«Хватит ли запаса», «Как настроено», «Перед обслуживанием» — и в каждой
строки в одну высоту: название, зачем это нужно, кнопка. Видно сразу всё, что
можно снять; раскрывается то, что попросили, и выбор запоминается.

Собранный блок помечен акцентом слева — не надо раскрывать все подряд, чтобы
вспомнить, что уже снято. Под выводом стоит время съёма и число строк, а
длинный вывод показывается окном с прокруткой, чтобы не выталкивать
остальную страницу за экран.

**Разбор моделью — по блоку и по всему сразу.** У каждого собранного блока
появляется кнопка «Разобрать»: она объясняет, что здесь важно и что делать.
Само по себе `Handler_read_rnd_next 4 млрд` ничего не говорит человеку,
который пришёл разбираться в аварии, а не изучать `performance_schema`.

Отдельная карточка сверху — «Разбор ИИ по кластеру». Она отдаёт модели всё,
что уже собрано на странице, разом. Это главное: самое важное обычно видно
не внутри одного блока, а на их пересечении — медленные запросы плюс
отставание реплики плюс `innodb_flush_log_at_trx_commit=1` складываются в
одну историю, а не в три. Чем больше блоков раскрыто, тем полнее разбор.

Разбирается то, что человек видит на экране: блоки уходят на сервер из
браузера. Пересобирать их заново значило бы объяснять другой срез — профиль
нагрузки через пять минут уже иной.

**Но экраном разбор не ограничен.** Раньше он видел только раскрытые блоки и
честно писал «нет метрик памяти, нет истории, нет планов выполнения» — хотя
всё это агенту доступно, просто никто не нажал кнопку. Теперь недостающее он
добирает сам, параллельно и с ограничением по времени на каждый кусок:

| Что добирается | Откуда |
|---|---|
| текущие метрики всех серверов, включая реплику и ядро | Prometheus |
| история за выбранный период и сравнение с той же неделей назад | Prometheus |
| память, своп и следы OOM | node_exporter + журнал ядра по SSH |
| планы выполнения тяжёлых запросов | `EXPLAIN` по данным performance_schema |

Уже собранное на экране второй раз не снимается: профиль нагрузки и планы
выполнения — это минуты работы сервера ради тех же строк. Недоступный сервер
не роняет разбор целиком: раздел пропускается, а в конце сказано, какой
именно и почему.

### Схема базы: снимается по кнопке, хранится у агента

Без схемы агент отвечает на вопросы про нагрузку, но не может ответить на
вопрос про данные. «Сколько договоров с отрицательным балансом» — вопрос к
базе, и чтобы написать такую выборку, надо знать имена таблиц и столбцов. Не
зная их, модель либо отказывается, либо выдумывает.

**Почему снимок, а не запрос каждый раз.** Обход `information_schema` на базе
с тысячами таблиц заметен на боевом сервере, а схема меняется раз в релиз, не
раз в минуту. Поэтому она снимается однажды, хранится в базе агента и
читается оттуда мгновенно, не трогая продуктив.

**Пересъёмка — действие администратора.** Это обращение к боевому серверу, и
запускать его походя не стоит; кнопка спрашивает подтверждение и говорит, чем
это обернётся. Обычный пользователь снимок только читает.

Что в снимке: базы с размерами, таблицы (крупные сверху), столбцы с типами,
ключами и комментариями, индексы с составом и кардинальностью. Пределы
сознательные — 20 баз, 80 таблиц на базу, подробности для 300 самых крупных
таблиц. Список из тысячи таблиц бесполезен и человеку, и модели; о том, что
осталось за кадром, снимок пишет прямо.

В чате модель получает короткую справку — какие есть базы и их крупные
таблицы по именам, — а подробности запрашивает инструментом `get_schema`
сама: по имени таблицы или поиском по куску имени. Последнее нужно чаще, чем
кажется: человек помнит, что «где-то есть про договоры», но не помнит —
`agreements`, `contracts` или `dogovor`.

```
GET  /api/schema/{кластер}                 — снимок целиком
GET  /api/schema/{кластер}?table=orders    — столбцы и индексы таблицы
GET  /api/schema/{кластер}?search=balance  — где встречается имя
POST /api/schema/{кластер}/snapshot        — снять заново (администратор)
```

### План выполнения как инструмент

`EXPLAIN` отвечает на вопрос, на который не отвечают метрики: почему именно
этот запрос медленный. «Выполняется 4 секунды» — наблюдение; «читает таблицу
целиком, хотя индекс есть, потому что статистика устарела» — причина и
действие.

На вкладке SQL две кнопки:

- **«План»** — для запроса в поле. Сам запрос при этом **не выполняется**:
  `EXPLAIN` только спрашивает оптимизатор, как он собирается его выполнять.
- **«План соединения»** — `EXPLAIN FOR CONNECTION` для запроса, который идёт
  **прямо сейчас**. Это ценнее в аварии: запрос виден в списке процессов, а
  воспроизвести его негде. Идентификатор берётся из блока «Что нагружает
  базу» на странице кластера — он стоит перед адресом.

Тем же инструментом пользуется и модель в чате: можно просто попросить
«объясни, почему этот запрос медленный», приложив текст.

**В диагностике план строится сам.** Профиль нагрузки («Что нагружает базу»)
берёт запросы, которые идут дольше пяти секунд, и объясняет их прямо на
работающем соединении — без отдельной кнопки и без попыток воспроизвести
запрос, параметры которого неизвестны. В отчёте остаются выводы, а не
пересказ плана:

```
  Планы выполнения для запросов, которые идут прямо сейчас:

  Соединение 771, идёт 88 с:
    SELECT `uid`, `balance` FROM `agreements` WHERE `archive` = 0
    [ВАЖНО] agreements — таблица читается целиком, хотя подходящий индекс есть
         ANALYZE TABLE agreements, затем посмотреть план снова
```

Схемы таблиц к таким планам не прикладываются: разбор идёт по горячим следам,
и лишние обращения к базе, которой и так плохо, там ни к чему.

**План не показывается как есть, а разбирается.** Шесть столбцов сокращений
читаются не всеми, а `Using filesort` значит не «использует сортировку», а
«сортирует без индекса, в памяти или на диске». Что агент вытаскивает:

| Что в плане | Что это значит | Что делать |
|---|---|---|
| `type=ALL`, но `possible_keys` не пуст | индекс есть, оптимизатор его не взял | `ANALYZE TABLE`, затем порядок столбцов в индексе |
| `type=ALL`, индексов нет | таблица читается целиком | индекс под условия `WHERE` и `JOIN` |
| `type=index` | читается весь индекс, а не диапазон | проверить, стоит ли первый столбец индекса в `WHERE` |
| `Using filesort` | сортировка без индекса, при объёме уходит на диск | индекс, где столбцы `ORDER BY` идут за столбцами равенства |
| `Using temporary` | временная таблица под `GROUP BY`/`DISTINCT` | индекс под группировку либо переписать запрос |
| `Using join buffer` | соединение без индекса | индекс на столбце соединения |
| `DEPENDENT SUBQUERY` | подзапрос выполняется для каждой строки | переписать через `JOIN` |

Оценки строк **перемножаются**, а не складываются: вложенные циклы — это
произведение. Тысяча на тысячу даёт миллион, и в плане это видно только так,
поэтому агент считает произведение сам и пишет его отдельной строкой.

К плану прикладываются схемы таблиц (до четырёх): рекомендация по индексам
без схемы — гадание, потому что неизвестно, какие индексы уже есть.

**Нужны ли отдельные права.** Обычно нет:

| Форма | Что нужно |
|---|---|
| `EXPLAIN SELECT …` | ровно те же права, что и на сам запрос, то есть `SELECT`. Отдельного права `EXPLAIN` в MySQL не существует |
| запрос через представление (`VIEW`) | **`SHOW VIEW`** сверх `SELECT` |
| `EXPLAIN FOR CONNECTION` для **чужого** соединения | **`PROCESS`** (он уже рекомендован для `SHOW PROCESSLIST` и `SHOW ENGINE INNODB STATUS`) |
| `EXPLAIN ANALYZE` (MySQL 8.0.18+) | те же права, но запрос **действительно выполняется** — ограничен `MAX_EXECUTION_TIME`, как и остальные |

```sql
-- если в запросах встречаются представления
GRANT SHOW VIEW ON *.* TO 'ai_agent'@'<IP>';
```

Сообщение сервера про нехватку прав здесь особенно недружелюбное: при
отсутствии `SHOW VIEW` он пишет «lacking privileges for underlying table»,
что звучит как нехватка `SELECT`. Агент распознаёт этот случай и называет
недостающее право с готовой командой.

### Память, своп и OOM

Самый неприятный вид аварии базы — тот, где база ни при чём. Ядру не хватило
памяти, оно выбрало самый жирный процесс и убило его; для сервера БД это
всегда `mysqld`. В метриках видно только следствие: занятость памяти за
секунду до смерти, потом провал и рост подключений. Причина остаётся в
журнале ядра, куда никто не смотрит, потому что смотрят в MySQL.

Агент смотрит в оба места сразу, потому что каждое по отдельности врёт:
node_exporter знает скорость и объёмы, но не знает, кого убили; журнал ядра
знает имя и время, но ничего не знает о том, что было до.

Своп считается отдельно от памяти и не по занятости. Занятый своп сам по
себе не беда — Linux может годами держать там страницы, к которым не
обращались. Беда — **активная подкачка**: страницы ездят туда-обратно, и
каждая обходится в дисковый доступ там, где ожидался доступ к памяти.
Поэтому смотрим `pswpin`/`pswpout` — сколько страниц переехало за час.

Отсутствие свопа тоже названо вслух: без него ядро при нехватке памяти не
замедляет процесс, а сразу убивает.

Журнал ядра читается тремя способами по очереди — `dmesg -T`, `journalctl -k`,
`/var/log/messages`: на новых ядрах `dmesg` закрыт для обычного пользователя
(`kernel.dmesg_restrict`), а доступ к journald есть не у всех учёток. Где-то
работает одно, где-то другое.

Кнопка «Спросить агента» переносит вопрос об этом кластере в чат уже
сформулированным.

**Действия на событии.** Под каждым алертом три кнопки: «Разобрать в чате»
подставляет вопрос с именем события, кластером и временем и сразу отправляет;
«Похожие случаи» показывает прошлые с записанными решениями; «Метрики
кластера» открывает его страницу. Раньше дежурный читал алерт и формулировал
всё это руками, попутно вспоминая имя кластера.

**Новое событие видно сразу.** Приходит по тому же WebSocket, что и чат:
всплывает уведомление, счётчик на вкладке растёт, открытый список
обновляется. Отдельного канала для этого не понадобилось.

**Видно, чем агент пользовался.** Под ответом — метки вызванных инструментов:
«профиль нагрузки», «логи серверов», «SQL-запрос». Сразу понятно, на чём
основан ответ, и заглядывал ли он вообще в логи.

**Вкладка SQL.** Только чтение, валидатор тот же, каждый запрос попадает в
журнал действий. Готовые запросы из диагностического набора выбираются
списком, последние двенадцать своих запоминаются в браузере.

### Как это выглядит

Интерфейс рос по частям, и это было видно: одни и те же по смыслу вещи —
отступы, скругления, размеры подписей — в каждом разделе оказывались чуть
разными. Величины сведены в один набор, и разделы берут их оттуда, а не
подбирают на глаз: шаг отступов в 4 пиксела, три радиуса скругления по роли
объекта, семь ступеней размера текста с заметной разницей между соседними —
иначе иерархия не читается, а «почти одинаковое» выглядит ошибкой.

Про шрифты: агент живёт в закрытом контуре, внешние шрифтовые сервисы там
недоступны. Поэтому характер набора задаётся не гарнитурой, а работой с
ней — шкалой, весом, разрядкой прописных подписей и вторым, моноширинным
семейством для данных: числа и вывод команд должны стоять в колонку.

**Значки вкладок нарисованы, а не набраны эмодзи.** Причина не во вкусе:
эмодзи берётся из шрифта системы, и 🩺 на рабочих машинах не отрисовался
вовсе — у вкладки просто не было значка. Свои значки — одной толщины линии,
в цвете текста, поэтому подсвечиваются вместе с активной вкладкой и не
зависят от того, какой шрифт установлен.

**Пустой раздел объясняет, а не командует.** Вместо «Нажмите „Проверить
сейчас“» — что здесь бывает и почему оно не появилось само: «Обход всех
серверов по SSH и пробный запрос к модели занимают до минуты, поэтому
проверка не начинается сама при открытии вкладки».

**Две темы, три состояния.** В шапке переключатель: «система», «тёмная»,
«светлая». Состояний именно три, и «как в системе» — не отсутствие выбора, а
самостоятельный режим: у кого система переключается по расписанию, тот хочет
того же и здесь. Явный выбор побеждает систему в обе стороны и переживает
перезагрузку.

Тёмная остаётся основной: агент открыт в дежурке весь день, часто рядом с
графиками Grafana, и светлый экран в этом ряду бьёт по глазам. Светлая —
равноправная, а не осветлённая тёмная: акцент и цвета состояния взяты темнее,
иначе на белом они не читаются.

| | Тёмная | Светлая |
|---|---|---|
| фон | `#0b0e14` | `#f3f5fa` |
| акцент | `#4c8dff` | `#1f63d6` |
| «всё хорошо» | `#38c172` | `#12763d` |
| «внимание» | `#e3a008` | `#8a6100` |
| «критично» | `#ef5350` | `#c02726` |

Контраст каждого цвета к каждой поверхности проверяется тестом и нигде не
опускается ниже 4,5 — это подписи, и «почти читается» тут не годится. Заодно
подняли приглушённый текст тёмной темы: прежний давал 3,6.

Нейтральные тона в обеих темах уведены в синеву, к акценту, а не взяты чистым
серым: чистый серый выглядит не выбранным, а доставшимся.

**Как это устроено внутри.** Все цвета — величины, в том числе составляющие
для полупрозрачных (`rgb(var(--accent-rgb) / .12)`). Цвет, зашитый прямо в
правило, одинаков в обеих темах: полупрозрачный синий, красивый на тёмном
фоне, на светлом превращается в грязь. Тест следит, чтобы таких не появилось
снова, и чтобы набор величин во всех трёх палитрах совпадал — цвет,
объявленный только в одной, даёт текст одной темы на фоне другой.

**Движение работает, а не украшает.** В мониторинге оно — ещё один способ
сказать «посмотри сюда»: число изменилось, пришло событие, связь пропала.
Поэтому анимируются только смены состояния:

| Что происходит | Что видно |
|---|---|
| обновились числа кластера в списке | изменившееся подсвечивается на мгновение — заметить рост лага иначе можно было, только сравнив с тем, что помнишь |
| пришло событие | счётчик на вкладке подскакивает, уведомление приезжает справа |
| идёт подключение | точка связи пульсирует — раньше «нет связи» и «подключаюсь» выглядели одинаково |
| раскрывается блок диагностики | высота едет от нуля, а не появляется рывком |
| строятся графики | разворачиваются слева направо, по направлению времени, со ступенькой между соседними |
| пришла реплика в чат | выезжает снизу; восстановленная переписка — нет, полсотни разом выезжающих реплик это рябь |
| агент сообщает о шаге работы | шаг въезжает сбоку: видно, что работа продвинулась, а не просто сменилась надпись |

Ничего не длится дольше трети секунды: интерфейс, который заставляет ждать
свою анимацию, раздражает уже на второй день. Ничего не появляется по
прокрутке — всё, что должно быть прочитано, видно сразу.

Системная настройка «меньше движения» уважается целиком: остаются только
смены состояния, выраженные цветом. Её ставят люди, которым от движения
физически плохо.

**Видимый фокус с клавиатуры** есть у всех элементов управления: без него
интерфейсом нельзя пользоваться без мыши. Движение отключается вместе с
системной настройкой `prefers-reduced-motion`.

### Пока идёт запрос

Раздел, который «просто ничего не показывает», выглядит как поломка: человек
не знает, идёт запрос или всё повисло. Везде, где команда уходит на сервер,
теперь крутится кольцо с подписью, чего ждём: «Снимаю два среза
performance_schema», «Читаю логи по SSH», «Опрашиваю Prometheus по всем
кластерам». Кольцо появляется в трёх местах сразу:

- **в самом разделе** — вместо пустоты;
- **на кнопке**, которая запустила команду, — видно, какая из нескольких
  работает, и повторное нажатие не проходит: два одновременных «Снять
  профиль» дают два SSH-захода и путаницу в выводе;
- **на вкладке** — раздел может грузиться, пока смотрят другой.

## Чаты

Разговоров у человека несколько: разбор ночной аварии и вопрос про настройку —
разные истории, и держать их в одной ленте значит портить контекст обеим.
Слева от переписки — список чатов: выбрать щелчком, создать кнопкой сверху,
переименовать и удалить — значками, которые появляются при наведении на
строку. Переименование правится прямо в списке: Enter сохраняет, Escape
отменяет.

У сегодняшних чатов в строке показано время последнего сообщения, у остальных
дата, и рядом число сообщений. На узком экране список убирается и вызывается
кнопкой ☰ над перепиской.

Список кластеров слева сворачивается кнопкой в его заголовке: при разборе по
логам и таблицам место важнее. Панель уезжает, оставляя узкую полоску с той же
кнопкой — так видно, куда её вернуть. Выбор запоминается в браузере.

Название берётся из первого вопроса, если не задать своё — список из «Новый
чат ×5» бесполезен. Рядом с названием видно время последнего сообщения и их
количество.

**Ответ не пропадает вместе со вкладкой.** Разбор долгого вопроса — это сбор
метрик, чтение логов и несколько ходов модели инструментами; терять его из-за
случайного F5 обидно. Ответ считает задача, привязанная к разговору, а не к
соединению: соединение пропало — генерация идёт дальше и в конце сама
сохраняет ответ в историю. Вернулись на страницу — агент отдаёт уже
накопленное и дописывает остаток на ваших глазах, о чём в ленте появляется
пометка. Вопрос при этом сохраняется до начала генерации, поэтому после
перезагрузки виден и он, а не пустой чат.

**Видно, чем агент занят.** Тяжёлый вопрос собирается минуту и дольше: два
среза `performance_schema`, `EXPLAIN` по десятку запросов, чтение логов по
SSH. Всё это время человек смотрел на три точки и не знал, работает агент
или завис. Теперь под ответом идёт список шагов — «Читаю метрики Prometheus
за 6 ч», «Снимаю профиль нагрузки», «Читаю логи на 10.0.0.7 по SSH», — и
исчезает, как только пошёл текст ответа: дальше о работе говорит он сам.

**Вызовы инструментов не попадают в чат.** Часть моделей не умеет штатный
tool calling, но обучена писать вызов прямо в ответ:

```
<tool_call><function><parameter=cluster>vladivostok</parameter>
<parameter=sql>SELECT ...</parameter></function></tool_call>
```

Формально модель сделала своё дело — просто её никто не слушал: агент
показывал разметку как обычный текст. Теперь такие вызовы вылавливаются из
потока, выполняются теми же функциями, что и штатные, а результат
возвращается модели, чтобы она дописала ответ по данным. Разметка до
пользователя не доходит ни при каком исходе — даже нераспознанный вызов
показывать незачем. Понимаются и JSON внутри тега, и разметка с
`<parameter=имя>`, и вызов вообще без имени функции: по набору параметров
видно, что имелось в виду.

Задача на разговор ровно одна: второй Enter, пока ответ не готов, подключает
к тому же ответу, а не запускает второй. «Остановить» прерывает генерацию по
идентификатору разговора, так что кнопка работает и в заново открытой вкладке.
Реестр задач живёт в памяти агента — перезапуск службы незавершённые ответы
обрывает, и такой вопрос проще задать заново.

| Метод | Что делает |
|---|---|
| `GET /chat/threads` | список своих чатов |
| `POST /chat/threads?title=…` | создать |
| `PATCH /chat/threads/{id}?title=…` | переименовать |
| `DELETE /chat/threads/{id}` | удалить вместе с перепиской |
| `GET /chat/history?thread={id}` | сообщения выбранного чата |
| `DELETE /chat/history?thread={id}` | очистить один чат |

В сокет к перечисленному добавились два сообщения: клиент шлёт `attach` с
`thread_id` при подключении и при переключении разговора, агент отвечает
`resume`, если для этого разговора ответ уже пишется.

Чужой чат не отдаётся и не удаляется, даже если знать идентификатор:
владелец сверяется на каждом обращении. Владелец — имя вошедшего
пользователя, а при выключенном входе — идентификатор браузера.

**Переписка от прежних версий не теряется.** Раньше история была одна сплошная,
и `session_id` хранил идентификатор соединения. При первом обращении такие
сообщения собираются в чат «Прежняя переписка» — новую колонку для этого
заводить не пришлось: `create_all` добавляет только отсутствующие таблицы,
но не колонки в существующие.

## Журнал действий, приём событий и сводка

**Журнал действий.** Отдельная вкладка для администраторов: входы и отказы во
входе, выдача и отзыв доступов, удаление событий, записанные решения,
выполненные SQL-запросы — с именем, адресом и подробностями. Раньше это
оседало в журнале systemd вперемешку с остальным выводом и пропадало после
ротации. Хранится год, фильтруется по действию и периоду; наружу отдаётся
через `GET /api/audit`.

Отдаётся **страницами по сто записей**: за месяц их набираются тысячи, и
вываливать всё разом значит подвесить браузер ради того, что человек всё
равно не прочитает. Кнопка «Показать ещё» дописывает следующую сотню к уже
показанному, а не перерисовывает список — иначе просмотренное место уезжает
и его приходится искать заново.

```
GET /api/audit?days=30&limit=100&offset=0&action=&username=
→ {"total": 2841,      ← сколько всего подходит под фильтр
   "returned": 100,    ← сколько отдано сейчас
   "offset": 0,
   "has_more": true,   ← есть ли что-то дальше
   "items": [...]}
```

`total` считает **все** подходящие записи, а не отданные: без этого
непонятно, есть ли продолжение, и «Показать ещё» приходилось бы нажимать
вслепую. Счётчик показывается всегда — «показано 40 из 40, это всё за
период» отвечает на вопрос не хуже кнопки.

**Панели «Журнал» и «Доступы» прокручиваются.** До 2.15.0 у них не было
прокрутки вовсе: на ноутбуке подвал со счётчиком и кнопкой «Показать ещё»
уезжал за нижний край и был недостижим — снаружи это выглядело как
отсутствие листания.

**Выданные доступы тоже листаются** — по пятьдесят, с фильтром по логину,
имени и роли: искать глазами в трёх сотнях строк это не поиск.

Запись идёт в **той же транзакции**, что и само действие: отдельная означала
бы вторую транзакцию поверх незакрытой первой, а SQLite допускает одного
писателя — журнал молча терялся бы именно на тех действиях, которые важнее
всего записать. Отказ во входе фиксируется до возврата ошибки, иначе откат
унёс бы запись с собой.

**Ограничение приёма событий.** `POST /api/alerts/ingest` проверял только
токен. Зациклившийся скрипт на стороне Zabbix за ночь залил бы таблицу
сотнями тысяч записей: лента нечитаема, память инцидентов бесполезна.

```bash
INGEST_RATE_PER_MIN="120"   # от одного отправителя; 0 — не ограничивать
```

Сверх предела приходит `429` с `Retry-After`. Ограничение считается по паре
«токен + адрес», то есть по отправляющей системе, а не суммарно.

**Сводка по расписанию.** Агент сам приходит с новостями: что случилось за
период, какие события и сколько раз, что деградировало относительно обычного
дня, какие реплики нездоровы и что осталось без записанного решения.

```bash
DIGEST_ENABLED="true"
DIGEST_AT="09:00"           # по времени сервера
DIGEST_HOURS="24"
DIGEST_TO="dba@company.ru,ops@company.ru"
DIGEST_WEBHOOK="https://mattermost.company.ru/hooks/..."
```

Почта берётся из тех же настроек, что и у Alertmanager. Последняя сводка
всегда доступна страницей `/digest` — на случай, если письмо не дошло или
почты нет вовсе. Собрать и разослать немедленно, не дожидаясь утра:
`POST /api/digest/send`.

## Устройство агента

Агент — асинхронное приложение на FastAPI, разложенное по слоям. Каждый слой
знает только про соседний снизу, поэтому любую часть можно читать и менять
отдельно:

| Слой | Что делает |
|------|------------|
| `agent/main.py` | сборка: middleware, подключение роутов, статика, жизненный цикл |
| `agent/api/routes/` | HTTP и WebSocket. Только приём запроса и вызов сервисов |
| `agent/api/deps.py` | зависимости: сессия базы, текущий пользователь, права |
| `agent/schemas/` | pydantic-схемы запросов и ответов, по ним строится Swagger |
| `agent/services/` | предметная логика: каталог, метрики, логи, SQL, модель |
| `agent/db/repositories/` | все обращения к таблицам собраны здесь |
| `agent/db/models.py` | модели SQLAlchemy |
| `agent/core/` | настройки и безопасность |

Всё, что ходит по сети, — асинхронное. Синхронные библиотеки, где без них
нельзя (`ldap3`, `pymysql`), уводятся в поток: держать на них цикл событий
значит подвесить весь агент, пока контроллер домена или база думает.

**Хранилище: SQLite по умолчанию, MySQL по желанию.** Данных немного —
события, история чата, доступы, оценки, — и файловая база рядом с агентом
покрывает обычный случай: ставить нечего, переживает рестарт. Если агентов
несколько или история нужна общая, переключитесь одной строкой в `config.env`:

```bash
DB_URL="mysql+asyncmy://agent:пароль@10.0.0.5:3306/ai_agent"
```

Схема создаётся сама, драйвер `install_agent.sh` ставит только при переходе
на MySQL — в закрытом контуре лишние пакеты не нужны. Пустой `DB_URL`
означает SQLite по пути `ALERTS_DB_PATH`.

Драйверы только асинхронные (`aiosqlite`, `asyncmy`): синхронный блокировал бы
цикл событий на каждом запросе.

**Существующие базы подхватываются как есть** — схема совпадает с прежней,
переносить данные не нужно. Время хранится строкой ISO-8601 в UTC, а не типом
`DATETIME`: так сравнение по периоду одинаково работает в обеих СУБД,
лексикографический порядок совпадает с хронологическим, и уже накопленные
базы читаются без преобразования.

**Проверки:**

```bash
python3 tests/test_agent.py     # поведение
python3 tests/test_names.py     # все ссылки на глобальные имена разрешаются
```

`test_names.py` разбирает байт-код каждой функции и проверяет, что все
загружаемые ею глобальные имена существуют. Ловит перенос функции без
переноса импорта — до выполнения этой ветки такое может пролежать неделю,
а проявляется обрывом соединения или пятисоткой.

`test_agent.py` — тридцать восемь проверок: слой данных, чтение и запись в базу прежнего формата и
приложение целиком — вход, права, выдача доступа, приём события, память
инцидентов, Swagger и разговор по WebSocket от начала до конца. Ни Prometheus,
ни LLM, ни каталог для них не нужны: реестр берётся временный, модель
подменяется заглушкой.

## Требования

| Компонент | Требование |
|-----------|-----------|
| ОС | Oracle Enterprise Linux 8 / RHEL 8 / Rocky 8 (dnf, systemd, firewalld) |
| Python | 3.9+ (ставится автоматически через dnf) |
| Сеть | Сервер мониторинга должен достигать: портов 9100/9104 всех MySQL-серверов, вашего LLM API, а также github.com и grafana.com — либо их зеркал (см. ниже). MySQL-серверы качают экспортёры сами, поэтому зеркало GitHub должно быть доступно и с них |
| pip | Публичный PyPI либо внутренний репозиторий — задаётся в `./configure.sh` (`PIP_INDEX_URL`) и прописывается в venv агента |
| Зеркала | Для закрытого контура: `GITHUB_BASE_URL` (бинари) и `GRAFANA_COM_URL` (дашборды) — подменяют домен, путь достраивается как на оригинале |
| LLM | Любой OpenAI-совместимый API: эндпоинт `POST {BASE_URL}/chat/completions`, поддержка `"stream": true` (SSE), авторизация `Authorization: Bearer <token>` |
| MySQL | 5.7+ / 8.0+, доступ root для создания пользователя `exporter` (или создать вручную) |
| SSH | Для авто-установки экспортёров: с сервера мониторинга SSH-доступ по ключу на MySQL-серверы под вашей учётной записью (`SSH_USER` из `config.env`), и для неё — `sudo` без пароля на этих серверах. Не обязательно — можно ставить вручную |

Мастер спросит:

### Шаг 3. Установить экспортёры на MySQL-серверах

Установка идёт по SSH под учётной записью из `config.env` (`SSH_USER`, спрашивается
в `./configure.sh`), а команды на MySQL-серверах выполняются через `sudo`.
Root-логин по SSH не нужен.

**Подготовка — один раз на каждом MySQL-сервере** (под root):

```bash
# 1. Пустить ключ учётки мониторинга (выполняется с сервера мониторинга)
ssh-copy-id dbadmin@10.1.0.1

# 2. Разрешить этой учётке sudo без пароля (на MySQL-сервере)
echo 'dbadmin ALL=(ALL) NOPASSWD: ALL' > /etc/sudoers.d/mysql_monit
chmod 440 /etc/sudoers.d/mysql_monit
visudo -c                      # проверка синтаксиса
```

**Вариант А — автоматически по SSH:**

```bash
./manage_cluster.sh install-exporters kemerovo
./manage_cluster.sh install-exporters novosibirsk

# разовое переопределение учётки/порта/ключа:
./manage_cluster.sh install-exporters omsk --user other_admin --port 2222 --key ~/.ssh/omsk_rsa
```

Перед установкой скрипт проверяет на каждом хосте SSH-доступ и `sudo -n true`,
и при неудаче печатает нужную строку для `/etc/sudoers.d/`. Проверка идёт сразу
по primary и replica, чтобы кластер не остался наполовину настроенным.

**Вариант Б — вручную** на каждом сервере (primary и replica):

```bash
scp scripts/install_exporters.sh dbadmin@10.1.0.1:/tmp/
ssh dbadmin@10.1.0.1
sudo env MYSQL_EXPORTER_PASSWORD='ваш_пароль_из_clusters.json' \
     bash /tmp/install_exporters.sh
```

Скрипт: откроет порты 9100/9104, поставит node_exporter + mysqld_exporter,
покажет SQL для создания пользователя `exporter` (или создаст сам, если передать
`MYSQL_ROOT_PASSWORD=...`), включит performance_schema и slow_query_log.

## Установка в закрытом контуре

Стек тянет извне три вещи, и каждая переопределяется в `./configure.sh`:

| Что качается | Откуда по умолчанию | Переменная |
|--------------|---------------------|------------|
| Prometheus, Alertmanager, node_exporter, mysqld_exporter | `https://github.com` | `GITHUB_BASE_URL` |
| Дашборды Grafana (1860, 7362, 11323, 7371) | `https://grafana.com` | `GRAFANA_COM_URL` |
| Python-зависимости агента | публичный PyPI | `PIP_INDEX_URL` |

Зеркала подменяют **только домен** (можно с префиксом пути), остальное скрипты
достраивают сами:

```
GITHUB_BASE_URL="https://my.ru/proxy"
  → https://my.ru/proxy/prometheus/node_exporter/releases/download/v1.8.2/node_exporter-1.8.2.linux-amd64.tar.gz

GRAFANA_COM_URL="https://my.ru/graf"
  → https://my.ru/graf/api/dashboards/1860/revisions/latest/download
```

Хвостовой слэш в URL допустим — он убирается автоматически.

⚠️ `GITHUB_BASE_URL` пробрасывается на MySQL-серверы по SSH: экспортёры качаются
**с них самих**, а не с сервера мониторинга. Зеркало должно быть доступно
и оттуда.

Остаётся один внешний источник, который пока не параметризован, — RPM-репозиторий
самой Grafana (`packages.grafana.com` в [install_monitoring.sh](scripts/install_monitoring.sh)).
Если Grafana ставится из внутреннего репозитория, замените блок `grafana.repo`
вручную или поставьте пакет заранее — скрипт пропускает установку, если
`grafana-server` уже есть.

## Сборка релиза

Версия хранится в файле `VERSION` (сейчас `1.0.0`). Сборка:

```bash
./scripts/make_release.sh                    # собрать dist/mysql-ai-monitoring-v1.0.0.zip
./scripts/make_release.sh --tag              # + создать локальный тег v1.0.0
./scripts/make_release.sh --tag --push       # + отправить тег в origin
./scripts/make_release.sh --tag --push --github   # + GitHub Release с приложенным архивом
```

По умолчанию скрипт **ничего не публикует** — только собирает архив в `dist/`.
Тег, push и Release включаются флагами явно.

### Ссылка на скачивание

После `--push` GitHub отдаёт архив тега сам, без ручной публикации:

```
https://github.com/Kertis90/monit_ai_mysql/archive/refs/tags/v1.0.0.zip
```

Скрипт печатает эту ссылку по завершении. Если нужен именно собранный нами
файл (а не автоматический архив GitHub) — используйте `--github`, тогда zip
приложится к Release как ассет:

```
https://github.com/Kertis90/monit_ai_mysql/releases/download/v1.0.0/mysql-ai-monitoring-v1.0.0.zip
```

### Почему секреты не утекут

Архив собирается через `git archive` — в него попадают **только отслеживаемые
файлы**. `config.env` (LLM-токен, пароль Grafana, хеш пароля админа,
`AUTH_SECRET`, пароль сервисной учётки LDAP) и базы `*.db` (алерты, чаты,
список доступов) перечислены в `.gitignore`, поэтому физически не могут
оказаться в архиве. После сборки скрипт дополнительно проверяет содержимое
и падает, если что-то из этого всё же обнаружилось.

Перед сборкой требуется чистое рабочее дерево — иначе версия в архиве
не соответствовала бы тегу.

### Поднять версию

```bash
echo "1.1.0" > VERSION
git add VERSION && git commit -m "Версия 1.1.0"
./scripts/make_release.sh --tag --push
```

## Переприменить все настройки

Изменили `config.env` или `clusters.json` — переприменить всё одной командой:

```bash
sudo ./scripts/install_all.sh
```

Скрипт идемпотентен: бинари не скачиваются заново (проверяется наличие),
но **все конфиги перегенерируются из `config.env` и `clusters.json`**, юниты
переписываются, сервисы перезапускаются.

Если конфиги «разъехались» и сервис не стартует — добавьте `--clean`:

```bash
sudo ./scripts/install_all.sh --clean
```

Тогда сгенерированные конфиги сначала удаляются, а потом создаются заново.
Данные (метрики, `grafana.db`, `alerts.db`) при этом сохраняются.

Порядок внутри: `install_monitoring.sh` → `install_agent.sh` → `manage_cluster.sh apply`.
`apply` идёт последним не случайно — он перезаписывает `prometheus.yml` целиком.

### Что перезаписывается, а что сохраняется

| Перезаписывается | Сохраняется |
|------------------|-------------|
| `/etc/prometheus/prometheus.yml` (через `apply`) | `/opt/ai-alert-agent/alerts.db` — алерты, чаты, список доступов |
| `/etc/prometheus/rules/*.yml` | `config.env` и `clusters.json` — источники правды |
| `/etc/alertmanager/alertmanager.yml` | Данные Prometheus в `/var/lib/prometheus` |
| Датасорс и дашборды Grafana | Дашборды, созданные вручную в Grafana |
| `/opt/ai-alert-agent/.env`, `agent/`, `web/` | Пароль Grafana (сбрасывается на значение из `config.env`) |
| systemd-юниты всех сервисов | |

Учётная запись Alertmanager создаётся как `alertmanager:reguser`
(группа задаётся переменной `ALERTMANAGER_GROUP`, по умолчанию `reguser`).
Если группы нет, скрипт её создаёт; если учётка уже была в другой группе —
переводит в нужную.

Пароль локального админа, `AUTH_SECRET` и выданные доступы не теряются:
первые два лежат в `config.env`, третьи — в `alerts.db`.

### Частичное переприменение

Когда нужно быстрее и без перезапуска всего:

```bash
sudo ./manage_cluster.sh apply       # только реестр: prometheus.yml + правила,
                                     # Prometheus перечитывает конфиг без рестарта
sudo ./scripts/update_llm.sh         # только настройки LLM в .env агента
sudo ./scripts/install_agent.sh      # только агент: .env, код, веб, рестарт
sudo ./scripts/install_monitoring.sh # только Prometheus/Alertmanager/Grafana
```

### Экспортёры

В `install_all.sh` они не входят — стоят на других серверах. Переприменять
отдельно, по кластеру:

```bash
./manage_cluster.sh install-exporters kemerovo
```

Повторный запуск безопасен: бинари не перекачиваются, но `.my.cnf`, юниты
и пароль экспортёра обновляются, сервисы перезапускаются.

### Проверить результат

```bash
./scripts/verify.sh
```

## Управление кластерами

```bash
./manage_cluster.sh list                       # таблица всех кластеров
./manage_cluster.sh add                        # добавить (интерактивно)
./manage_cluster.sh show kemerovo              # детали
./manage_cluster.sh disable kemerovo           # приостановить мониторинг
./manage_cluster.sh enable kemerovo            # возобновить
./manage_cluster.sh remove kemerovo            # удалить из реестра
./manage_cluster.sh install-exporters omsk     # экспортёры по SSH (SSH_USER + sudo)
./manage_cluster.sh install-exporters omsk --user dbadmin   # другая учётка разово

sudo ./manage_cluster.sh apply                 # ⚠ ПОСЛЕ ЛЮБЫХ ИЗМЕНЕНИЙ
```

`apply` делает три вещи: генерирует `prometheus.yml` со всеми enabled-кластерами
(с метками `cluster`, `cluster_label`, `role`), перезагружает Prometheus без
рестарта (`/-/reload`), копирует реестр агенту и перезапускает его.

## Чат и API

### Примеры вопросов в чате

| Вопрос | Что делает агент |
|--------|-----------------|
| «Как дела в Кемерово?» | Текущие метрики kemerovo |
| «Вчера в Новосибирске было плохо. Почему?» | История 30ч (min/avg/max + время пиков) + текущие |
| «За последние 3 часа в Омске вырос slow query rate» | История 3.5ч |
| «Какой кластер хуже всего себя чувствует?» | Сводка по всем кластерам |
| «Есть ли лаг репликации где-нибудь?» | Сводка по всем кластерам |
| «Какие были алерты вчера?» | История алертов из БД за 30ч |
| «Покажи инциденты по Кемерово за неделю» | Алерты kemerovo за 170ч + метрики |
| «Были ли сбои на прошлой неделе?» | Алерты по всем кластерам за период |

Распознавание города работает с падежами: «в Кемерове», «Новосибирска» — найдётся.
Распознавание времени: «вчера», «позавчера», «за N часов», «N часов назад»,
«утром», «за сутки», «за неделю».

**Исторические данные.** Период распознаётся из фразы: «вчера», «за 3 часа»,
«за 30 минут», «за 5 дней», «за 2 недели», «за месяц», «на прошлой неделе»,
«сегодня». Если период не назван, но вопрос про историю — «покажи динамику»,
«был ли рост», «какая статистика» — берётся окно **24 часа** по умолчанию.

История собирается и когда город не назван: раньше в этом случае в контекст
уходил только текущий статус, и агент отвечал, что исторических данных нет.

**Детальная статистика по интервалам.** Просьба «дай статистику», «покажи
метрики», «по ресурсам», «детально», «с разбивкой по 5 минут», «таблицей» —
агент кладёт в контекст не агрегаты, а **значения по каждому интервалу**: CPU, iowait,
память, load average, чтение и запись с дисков, сеть, QPS, медленные запросы,
подключения.

```
## Детальная статистика Кемерово: шаг 5 мин, период 6 ч, точек 72
  время           CPU%  iowait%     MEM%      LA1  diskR/s  diskW/s      QPS
  07.09 04:15     18.0      1.2     61.0      2.1    120.5k   3.4M      842
  07.09 04:20     74.0     22.8     63.0      9.7    980.2k  11.1M      301
```

По такой таблице видно то, чего не видно по min/avg/max: **когда именно** был
всплеск и с чем он совпал по времени.

**Таблица строится на каждый сервер кластера отдельно.** У кластера с репликой
серверов два, ресурсы у них разные, и сводить их в одну таблицу неверно —
в заголовке видно, чей это сервер:

```
## Детальная статистика Владивосток · primary 10.7.0.1: шаг 5 мин, период 6 ч
## Детальная статистика Владивосток · replica 10.7.0.2: шаг 5 мин, период 6 ч
```

Город называть не обязательно: если он не указан, таблицы строятся по всем
кластерам, а бюджет строк делится между ними и их серверами.

Период понимается и словами, без цифр: «за последний час», «за полчаса»,
«за пару часов», «за последние сутки», «за последнюю неделю».

Шаг задаётся фразой («по 30 секунд», «по часам»), по умолчанию 5 минут. Если
точек выходит больше `SERIES_MAX_ROWS` (200), шаг увеличивается автоматически —
об этом написано в заголовке таблицы, значения не подменяются молча.

**Максимум — сутки.** Окно метрик ограничено `MAX_METRICS_HOURS` (24 ч).
Если запросили больше, отдаётся последние 24 ч, и агент **обязан предупредить
об этом в ответе** — в контекст кладётся явная пометка, что период урезан.
Ограничение касается только метрик; история алертов живёт своим сроком
(`ALERTS_RETENTION_DAYS`, 30 дней).

Данные **уже хранятся**: Prometheus пишет метрики с интервалом 15 с и держит
их `PROMETHEUS_RETENTION` (по умолчанию 30 дней) в `/var/lib/prometheus`.
Агент ничего не дублирует — только читает и прореживает до нужного шага.
Нужна большая глубина — увеличьте `PROMETHEUS_RETENTION` и место под данные.

Выгрузка тех же данных, в том числе в CSV для Excel:

```bash
curl -s 'http://localhost:5001/api/series/kemerovo?hours=6&step=300' | python3 -m json.tool
curl -s 'http://localhost:5001/api/series/kemerovo?hours=24&step=300&format=csv' -o stats.csv
```

**Разметка ответов.** Ответ агента отображается размеченным, а не сплошным
текстом:

| Что в ответе | Как показывается |
|--------------|------------------|
| Таблица (markdown или выравненная агентом) | настоящая `<table>`, числовые колонки прижаты вправо, широкие прокручиваются внутри себя |
| Блок ``` ``` ``` | подсвеченный блок с меткой языка и кнопкой «копировать» |
| `код` в строке, `**жирный**`, `*курсив*` | соответствующее оформление |
| `## Заголовок`, списки `-` и `1.` | заголовки и списки |

Пока ответ печатается, показывается простой текст — перерисовывать разметку
на каждом токене дорого; готовый ответ размечается целиком. Восстановленная
из истории переписка тоже показывается размеченной.

Разметка своя, без библиотеки: в закрытом контуре её неоткуда взять.
**HTML экранируется до расстановки тегов**, поэтому текст от LLM не может
вставить свои теги — проверено восемью вариантами внедрения (`<script>`,
`onerror`, `javascript:`, `<iframe>`, попытки внутри таблицы и блока кода).

**Графики в чате.** Под ответом появляется компактная строка:

```
📈 Графики за 6 ч        📄 Выгрузить PDF
```

Графики **не рисуются сами по себе** — разворачиваются по клику и встраиваются
в само сообщение, а не вываливаются отдельной стеной под ним. Десять панелей
под каждым ответом про метрики мешали читать сам ответ.

Если графики попросили явно («покажи график QPS», «нарисуй», «в картинках»),
блок разворачивается сразу. Пока не развернули, запросы в Prometheus не идут
вообще — строка предложения данных не содержит.

Панели: QPS, медленные запросы, подключения и процент от лимита, InnoDB hit
rate, CPU, iowait, память, дисковый I/O и отставание реплики (последняя —
только если реплика есть). Раскладываются в две колонки, компактно.

Рисуются инлайновым SVG в браузере: библиотека графиков не подключалась —
в закрытом контуре CDN недоступен, а тащить её ради линии с сеткой избыточно.

Данные можно взять и напрямую:

```bash
curl -s 'http://localhost:5001/api/charts/kemerovo?hours=24' | python3 -m json.tool
curl -s 'http://localhost:5001/api/charts/kemerovo?hours=6&keys=qps,cpu,iowait'
```

**Отчёт в PDF.** Ссылка **📄 Выгрузить PDF** в той же строке под ответом
(если в вопросе была просьба выгрузить или распечатать — подсвечивается).
Открывает печатную страницу `/report?cluster=<имя>&hours=<часов>`: таблица
сводки (сейчас / среднее / мин / макс по каждому показателю) и все графики,
свёрстанные под печать — карточки не разрываются между страницами, кнопки
в печать не попадают.

PDF формирует **браузер** (кнопка «Сохранить в PDF» → диалог печати). Серверного
рендера намеренно нет: он потребовал бы `weasyprint` или `reportlab` с
системными библиотеками, а у вас закрытый pip-репозиторий. Если нужен именно
файл с сервера — например, для рассылки отчётов по расписанию без участия
человека — это отдельная задача, скажите.

Страницу можно открыть и напрямую, без чата:

```
http://MONITORING_IP:5001/report?cluster=kemerovo&hours=24
```

**Суммаризация длинной переписки.** Когда история упирается в
`CHAT_CONTEXT_MESSAGES` (по умолчанию 16 сообщений), вытесняемая часть не
выбрасывается, а сжимается LLM в короткую выжимку: какие кластеры обсуждали,
что нашли, к каким выводам пришли (включая «проблемы нет»), какие значения
назывались. Выжимка сохраняется в БД с ролью `summary` и уходит в контекст
как системное сообщение, поэтому агент не «забывает» ранее разобранное —
например, что плановая задержка реплики уже признана нормой.

После рестарта агента разговор восстанавливается от последней выжимки, а не
с обрывка последних реплик. Если выжимку построить не удалось (LLM недоступна),
поведение откатывается к прежнему — простой обрезке.

**История алертов в чате.** Если в вопросе есть слова про алерты, инциденты,
сбои, аварии или «что случилось», агент дополнительно достаёт записи из
`alerts.db` и кладёт их в контекст LLM: время, severity, кластер, инстанс,
краткое описание и — для трёх последних — прошлый разбор от LLM. Работают
те же фильтры, что и в остальном чате: если назван город, выборка сузится до
него; если назван период, окно ограничится им (но не шире `ALERTS_RETENTION_DAYS`).
Без указания периода берутся последние 30 дней, не больше 20 записей.

Блок подмешивается только по ключевым словам — чтобы обычные вопросы про
текущие метрики не таскали лишнее в промпт.

## WebSocket-протокол

Эндпоинт: `ws://IP:5001/ws` (или `wss://` за nginx — см. ниже).

**Клиент → сервер:**
```json
{"type": "message", "text": "Как дела в Кемерово?", "session_id": "my-session"}
{"type": "ping"}
```

**Сервер → клиент:**
```json
{"type": "context", "cluster": "Кемерово", "hours": 30}   // что определил агент
{"type": "token",   "text": "Судя"}                        // стриминг токенов
{"type": "token",   "text": " по"}
{"type": "done"}                                           // конец ответа
{"type": "error",   "text": "..."}
{"type": "pong"}
```

`session_id` хранит историю диалога (последние 8 пар) — можно задавать
уточняющие вопросы («а что с репликацией там же?»).

Пример клиента на Python:
```python
import asyncio, json, websockets

async def main():
    async with websockets.connect("ws://IP:5001/ws") as ws:
        await ws.send(json.dumps({"type": "message",
                                  "text": "Как дела в Кемерово?"}))
        while True:
            msg = json.loads(await ws.recv())
            if msg["type"] == "token": print(msg["text"], end="", flush=True)
            elif msg["type"] == "done": break

asyncio.run(main())
```

Встроенный веб-клиент (`web/app.js`) умеет: автопереподключение с экспоненциальной
задержкой, keepalive-ping каждые 25с, мигающий курсор при стриминге, чипы
контекста (какой кластер/период определён), панель кластеров с живыми бейджами.

## Алерты

Все правила используют метки, поэтому работают для любого количества кластеров
без правок:

| Алерт | Условие | Severity |
|-------|---------|----------|
| MySQLDown | mysql_up == 0 | critical |
| MySQLConnectionsCritical | > 95% max_connections | critical |
| MySQLHighConnections | > 80% | warning |
| MySQLSlowQueriesHigh | > 5/s | warning |
| MySQLInnoDBBufferPoolLowHitRate | hit rate < 95% | warning |
| MySQLHighRowLockWaits | > 10/s | warning |
| MySQLQPSDropped | падение QPS > 50% за 10 мин | warning |
| ReplicationIOThreadDown / SQLThreadDown | thread не работает | critical |
| ReplicationLagWarning / Critical | отставание **сверх плана** > 10s / > 60s | warning / critical |
| ReplicaNotReadOnly | реплика принимает запись | critical |
| HighCPUUsage / HighMemoryUsage | > 85% / > 90% | warning |
| DiskSpaceLow / Critical | < 15% / < 5% | warning / critical |
| HighDiskIOWait | > 20% | warning |

Маршрутизация: **critical** → AI-агент + email (если настроен);
**warning** → только AI-агент. При алерте агент собирает текущие метрики +
историю за 2ч, отправляет в LLM и сохраняет диагноз — виден во вкладке
«Алерты» веб-интерфейса и через `/alerts/history`.

### Приём алертов из внешних систем (Zabbix и др.)

Кроме Alertmanager алерты можно присылать по API: агент разберёт их через LLM
и положит в ту же историю, где их потом посмотрит дежурный.

```bash
INGEST_TOKENS="<токен>"     # config.env, спрашивается в ./configure.sh
                            # несколько токенов — через запятую
```

Внешняя система не умеет логиниться cookie, поэтому у эндпоинта своя
авторизация по токену — `X-API-Key` или `Authorization: Bearer`:

```bash
curl -X POST http://MONITORING_IP:5001/api/alerts/ingest      -H 'X-API-Key: <токен>' -H 'Content-Type: application/json'      -d '{
       "alert":    "Free disk space is low",
       "severity": "critical",
       "cluster":  "kemerovo",
       "instance": "10.1.0.1",
       "summary":  "/var: свободно 8%",
       "description": "Триггер Zabbix: vfs.fs.size[/var,pfree] < 10",
       "source":   "zabbix"
     }'
```

| Поле | Обязательно | Смысл |
|------|-------------|-------|
| `alert` | да | имя события |
| `severity` | нет | `critical` / `warning` / `info`, иначе `warning` |
| `cluster` | нет | имя из `clusters.json` — если совпало, в разбор пойдут метрики и история кластера |
| `instance` | нет | хост или хост:порт |
| `summary` | нет | краткое описание |
| `description` | нет | подробности от внешней системы |
| `source` | нет | `zabbix`, `nagios`, `custom`… по умолчанию `api` |

Если `cluster` совпал с реестром, агент подложит в разбор текущие метрики
и историю за 2 часа. Не совпал — разберёт по описанию события, но алерт
всё равно сохранится.

Настройка в Zabbix: **Оповещения → Способы оповещения → Webhook**, URL
эндпоинта, заголовок `X-API-Key`, тело — JSON выше с макросами
(`{TRIGGER.NAME}`, `{HOST.CONN}`, `{TRIGGER.SEVERITY}`).

Без `INGEST_TOKENS` эндпоинт отвечает `503` — приём выключен.

### Источник алерта

В списке алертов у каждой записи есть метка источника: **Prometheus**,
**Zabbix**, **API** и т.д. Записи, созданные до появления этой колонки,
при первом запуске помечаются как `prometheus` (миграция выполняется
автоматически, данные не теряются).

### Память инцидентов

У каждой записи в истории есть кнопка **«Записать решение»** — дежурный
пишет, чем инцидент закончился и что помогло. При следующем таком же алерте
эта запись попадает в разбор, и агент предлагает проверенное решение вместо
вывода с нуля.

```bash
curl -X POST http://localhost:5001/api/alerts/42/resolve      -H 'Content-Type: application/json'      -d '{"resolution":"Кончилось место на /var, почистили бинлоги"}'

curl -s http://localhost:5001/api/incidents/MySQLDown | python3 -m json.tool
```

Поиск идёт по имени алерта: сначала записи по тому же кластеру, потом по
любому — решение с соседней площадки обычно подходит.

Ценность прямо зависит от дисциплины: **не заполнять поле — не получить
пользы**. Зато заполненное один раз работает дальше само.

Поля добавляются к существующей БД миграцией при первом запуске, данные
не теряются.

### Меньше шума в алертах

Две меры против того, чтобы один инцидент разбирался LLM по нескольку раз.

**Подавление производных в Alertmanager.** Раньше было одно грубое правило
«critical глушит warning». Теперь шесть:

| Источник | Что глушит |
|----------|-----------|
| `MySQLDown` | **все** алерты того же сервера — репликация, QPS и подключения отвалились именно из-за этого |
| `Replication(IO\|SQL)ThreadDown` | `ReplicationLag*` — отставание вторично |
| `MySQLConnectionsCritical` | `MySQLHighConnections` |
| `ReplicationLagCritical` | `ReplicationLagWarning` |
| `DiskSpaceCritical` | `DiskSpaceLow` |
| любой `critical` | `warning` того же кластера |

Без первого правила упавший MySQL порождал пять-шесть алертов, и **каждый**
уходил в агента отдельным запросом к LLM на разбор одной и той же причины.

**Дедупликация повторов в агенте.** Alertmanager повторяет неразрешённый
алерт по `repeat_interval`. Повтор того же алерта на том же сервере в течение
`ALERT_DEDUP_MINUTES` (60) не отправляется в LLM заново — в историю
записывается разбор от предыдущего срабатывания.

`repeat_interval` увеличен с 4 до 12 часов: чаще напоминать о том же
инциденте смысла нет.

### Удаление ложных срабатываний

Записи истории удаляются из вкладки «Алерты» кнопкой **✕ Удалить** — она видна
только администраторам. Или через API:

```bash
# одну запись (id виден в /alerts/history)
curl -X DELETE http://localhost:5001/api/alerts/42

# все записи одного типа — когда ошибочное правило нагенерировало пачку
curl -X DELETE 'http://localhost:5001/api/alerts?name=ReplicationLagCritical'
```

Чистить историю стоит не только ради порядка: ложные записи попадают в контекст
ИИ при вопросах про инциденты и искажают разбор следующих проблем.

Если агент недоступен, можно и напрямую в БД:

```bash
sqlite3 /opt/ai-alert-agent/alerts.db   "SELECT id, ts, alert, cluster_label FROM alerts ORDER BY ts DESC LIMIT 20;"
sqlite3 /opt/ai-alert-agent/alerts.db "DELETE FROM alerts WHERE id IN (41, 42);"
```

⚠️ Удаление записи из истории **не гасит сам алерт**, если он всё ещё активен
в Alertmanager — тогда он придёт снова. Сначала устраните причину (или
исправьте правило и выполните `sudo ./manage_cluster.sh apply`), и только
потом чистите историю.

### Реплики с намеренной задержкой (MASTER_DELAY)

Если реплика поднята как «отложенная» (`CHANGE MASTER TO MASTER_DELAY=7200`),
её `Seconds_Behind_Master` **всегда** равен этой задержке. Алертить по нему
нельзя — `ReplicationLagCritical` горел бы непрерывно, а AI-агент на каждое
срабатывание тратил бы запрос к LLM на разбор несуществующей аварии.

Задержка задаётся у каждого кластера в [clusters.json](clusters.json)
(спрашивается в `./manage_cluster.sh add`):

```json
{
  "name": "kemerovo",
  "replica_ip": "10.1.0.2",
  "replica_delay_seconds": 7200,
  ...
}
```

**Источник задержки — сама реплика.** Правило берёт `SQL_Delay` из
`SHOW SLAVE STATUS` (метрика `mysql_slave_status_sql_delay`), а
`replica_delay_seconds` из реестра применяется, только если экспортёр эту
метрику не отдаёт. Поменяли `MASTER_DELAY` на реплике — дашборд и алерты
считают по-новому сразу, править реестр не нужно.

`./manage_cluster.sh apply` генерирует
`/etc/prometheus/rules/replication_delay.yml` с двумя recording rules:

| Метрика | Смысл |
|---------|-------|
| `mysql:replica_effective_lag_seconds` | отставание **сверх** плановой задержки — по ней алерты и дашборд |
| `mysql:replica_configured_delay_seconds` | сама плановая задержка — пунктиром на графике |

Алерты и дашборд используют первую: `0` значит реплика идёт ровно по графику,
`3600` — отстала на час сверх положенного. `replica_delay_seconds: 0` (или
отсутствие поля в старом реестре) даёт прежнее поведение — алерты по сырому
отставанию.

В чате агент показывает три величины раздельно — `replication_lag_raw_s`,
`replication_planned_delay_s` и `replication_lag_over_plan_s` — и берёт их из
того же recording rule, что питает дашборд, чтобы цифры в чате и на графике
не расходились. В системном промпте есть правило судить о репликации только
по отставанию сверх плана, с разобранным примером `raw=7217, planned=7200,
over_plan=17 — это норма`.

Проверить, что задержка видна Prometheus:

```bash
curl -s 'http://localhost/prometheus/api/v1/query?query=mysql_slave_status_sql_delay'   | python3 -m json.tool
curl -s 'http://localhost/prometheus/api/v1/query?query=mysql:replica_effective_lag_seconds'   | python3 -m json.tool
```

Если первая метрика пуста — экспортёр не отдаёт `SQL_Delay`, и тогда работает
запасной путь: значение `replica_delay_seconds` из реестра, которое надо
заполнить вручную.

⚠️ Порядок важен: `install_monitoring.sh` кладёт алерты, которые ссылаются на
`mysql:replica_effective_lag_seconds`, а саму метрику создаёт `apply`. До
первого `apply` эти два алерта просто не срабатывают (пустой результат), ложных
срабатываний не будет, но и реальный лаг не поймается — не забудьте
`sudo ./manage_cluster.sh apply`.

### Сохранение чатов по пользователям

Переписка сохраняется в ту же SQLite (`/opt/ai-alert-agent/alerts.db`, таблица
`chat_messages`) и восстанавливается при следующем открытии страницы — раньше
история жила только в памяти процесса и терялась даже при F5.

**Как опознаётся пользователь.** Если аутентификация включена, история
привязана к **имени вошедшего пользователя** — агентом пользуются несколько
человек, и переписка одного не должна попадать в контекст другого. Один
человек с ноутбука и с телефона видит одну историю, двое за одной машиной —
разные.

Если аутентификация выключена, история привязана к браузеру: при первом заходе `web/app.js` генерирует `crypto.randomUUID()` и
кладёт его в `localStorage` под ключом `mysql-ai-agent.client_id`. Он и уходит на
сервер с каждым сообщением.

> Чистый отпечаток браузера (canvas/шрифты/UA) для идентификации **не
> используется**: на одинаковых корпоративных машинах он совпадает, и
> пользователи видели бы переписку друг друга. Отпечаток всё же считается
> (короткий хеш UA, языка, экрана, таймзоны) и пишется в колонку `fingerprint` —
> но только как диагностическая метка, не как идентичность.

Следствия, о которых стоит знать:

| Ситуация | Что будет с историей |
|----------|----------------------|
| F5, перезапуск браузера | сохраняется |
| Другой браузер или другой профиль | отдельная история |
| Режим инкогнито | своя история, пропадёт с окном |
| Очистка данных сайта | история на сервере останется, но станет недоступна — выдастся новый `client_id` |
| Один браузер на двоих | общая история (это не аутентификация) |

```bash
CHATS_RETENTION_DAYS=30       # config.env, спрашивается в ./configure.sh
CHAT_CONTEXT_MESSAGES=16      # сколько последних сообщений уходит в LLM как контекст
```

API:

```bash
curl -s 'http://localhost:5001/chat/history?client_id=<uuid>&limit=50' | python3 -m json.tool
curl -X DELETE 'http://localhost:5001/chat/history?client_id=<uuid>'
```

В интерфейсе есть кнопка **«Очистить историю»** в шапке — она удаляет записи
этого браузера на сервере.

⚠️ Хранилище не шифруется, и любой, кто знает чужой `client_id`, может прочитать
его переписку через API. Для внутреннего инструмента это обычно приемлемо, но
если чат будет доступен снаружи — закрывайте его аутентификацией на nginx.

### Чтение логов серверов

Агент читает **slow-лог MySQL** с серверов БД и **логи ядра системы**
(Lanbilling) — с сервера ядра. Спросите «посмотри slow лог за час», «что в логах биллинга
вчера» — и логи попадут в разбор вместе с метриками.

Пути задаются у кластера в [clusters.json](clusters.json):

```json
"app_ip":                "10.1.0.10",
"slow_log_path":         "/var/log/mysql/slow.log",
"replica_slow_log_path": "",
"app_log_dirs":          "/var/log/billing,/var/log/billing/archive_logs",
"app_log_pattern":       "*.log*"
```

**Три адреса, три источника.** Slow-лог читается с **каждого** сервера БД —
и с primary, и с replica; нагрузка на них разная, и медленные запросы там
тоже разные. Логи ядра лежат на своём сервере (`app_ip`) и читаются один раз,
а не по разу на каждый сервер БД.

| откуда | что читается | поле |
|---|---|---|
| `primary_ip` | slow-лог | `slow_log_path` |
| `replica_ip` | slow-лог | `replica_slow_log_path`, пусто — как на primary |
| `app_ip` | логи ядра | `app_log_dirs` + `app_log_pattern` |

`app_ip` пустой — считаем, что ядро стоит на primary. `replica_slow_log_path`
нужен, когда на реплике другой диск или другое имя файла; для архивов есть
`replica_slow_log_archive_dir`.

У каждого из трёх серверов **свой часовой пояс**: период приводится к времени
того сервера, с которого читаем, — иначе `grep` шёл бы не по тем датам.

`slow_log_path` — путь к **текущему** логу. Ротированные соседи
(`slow.log.1`, `slow.log-20260907.gz`) подхватываются автоматически: из пути
берётся каталог и маска `slow.log*`. Если архивы slow-лога лежат отдельно,
добавьте необязательный `slow_log_archive_dir`.

Сжатые файлы читаются **`zgrep` напрямую** — распаковывать на диск не нужно.
Маска `*.log*` ловит и текущие `app.log`, и архивные `app.log.2.gz`.

**Как читается, чтобы не подавиться гигабайтами.** Файл целиком не читается
никогда:

1. `find … -printf` собирает **метаданные**: размер и время изменения. Логи
   приложения режутся по размеру, а не по дате, поэтому по имени файла период
   не определить — только по `mtime`.
2. Выбираются файлы, изменённые внутри запрошенного окна, **плюс один
   предыдущий**: при ротации по размеру запись за начало периода обычно
   оказывается в нём.
3. Файл больше 256 МБ сначала **делится пополам** до нужного места по
   времени (см. «Логи в несколько гигабайт»), и `grep` получает десятки
   мегабайт вместо десятков гигабайт.
4. `grep -F` по датам с `tail -n` (`LOG_MAX_LINES`, 400); для `.gz` —
   `zgrep`, тоже без распаковки. Поиск идёт с `LC_ALL=C` — побайтно вместо
   UTF-8, на гигабайтных файлах это в разы быстрее.
5. Чтение ограничено `LOG_READ_TIMEOUT` (180 с) — отдельно от времени
   подключения: соединение либо устанавливается за секунды, либо не
   устанавливается вовсе, а чтение большого лога идёт заметно дольше.

**Окно отсчитывается от времени сервера, а не агента.** Перед чтением агент
спрашивает у сервера `date` и берёт оттуда и абсолютное время, и локальное со
смещением пояса. Файлы отбираются по `mtime` — это Unix-время, одинаковое
везде; строки внутри — по меткам, а они написаны в поясе сервера. Смешивать
нельзя: Владивосток и Кемерово различаются на четыре часа.

**В шаблон входит час, а не только дата.** Раньше отбор шёл по дате, и запрос
«логи за последние два часа» возвращал целые сутки, обрезанные по числу строк
с конца. Теперь для узкого окна (до 26 часов) строятся шаблоны вида
`11.09.2026 09:`, и в выводе оказывается именно запрошенное окно. На широком
окне агент возвращается к отбору по суткам: шаблонов по часам стало бы больше,
чем строк в ответе.

**Slow-лог пересчитывается в UTC.** Начиная с MySQL 5.7.2 переменная
`log_timestamps` по умолчанию равна `UTC`: сервер живёт во Владивостоке, а в
slow-логе стоит время на семь часов назад. Отсюда и брались «не те» строки —
запрашиваешь последние два часа по местному времени, а в файле это время
наступит только к вечеру. Для таких файлов окно пересчитывается из
абсолютного времени, которое от пояса не зависит вовсе; локальные шаблоны при
этом остаются — в одном каталоге могут лежать логи, писанные и так и так.

В заголовке блока написано, за какой период отбирали и по чему:

```
### Логи приложения 10.0.0.7
  Период: 11.09 08:00 — 11.09 10:00 по времени сервера
  Отбор по дате и часу; просмотрено файлов: 2 из 14
```

**Форматы дат.** `grep` ищет фиксированными строками сразу во всех
распространённых видах, потому что каждый лог пишет по-своему:

| Шаблон | Где встречается |
|--------|-----------------|
| `2026-09-07` | slow-лог MySQL 5.7+, syslog, большинство сервисов |
| `260907` | slow-лог MySQL 5.6 и старше |
| `07.09.2026` | логи приложения: `07.09.2026 17:30:01.123456 DEBUG LWP410005 [file.cpp:func] текст` |
| `07/09/2026` | веб-серверы и часть приложений |

⚠️ **Slow-лог может быть в UTC.** Начиная с MySQL 5.7.2 переменная
`log_timestamps` по умолчанию `UTC`, то есть метки в slow-логе отличаются от
локального времени сервера, хотя лог приложения рядом пишется в локальном.
Поэтому для slow-лога дополнительно берутся соседние сутки — иначе на границе
дня поиск промахнулся бы на день. Проверить у себя:

```sql
SHOW VARIABLES LIKE 'log_timestamps';
```

`SYSTEM` — метки в локальном поясе, `UTC` — в UTC.

**Часовые пояса.** У серверов они разные (Владивосток и Кемерово — 4 часа),
поэтому используются **два разных отсчёта**, и смешивать их нельзя:

| Для чего | Какое время | Почему |
|----------|-------------|--------|
| Выбор файлов по `mtime` | абсолютное (Unix-время) | `mtime` одинаков независимо от пояса |
| `grep` по меткам внутри лога | локальное время сервера | метки пишутся в его поясе |

Оба значения агент берёт у самого сервера одной командой `date`, вместе
со смещением. Пояс указывается в заголовке блока, чтобы при сравнении двух
серверов было видно, что «10:00 там» и «10:00 здесь» — разные моменты.

**Доступ.** Идёт по SSH под учёткой, указанной при развёртывании —
`SSH_USER`/`SSH_PORT`/`SSH_KEY` из `config.env`, той же, что ставит экспортёры.
Отдельной учётки для чтения логов заводить не нужно. Агент работает от пользователя `aiagent`, поэтому ключ
должен быть доступен ему:

```bash
sudo -u aiagent ssh -i /путь/к/ключу dbadmin@10.1.0.1 'date'
```

Если команда не проходит, логи читаться не будут — агент скажет об этом прямо,
а не промолчит.

**Если файлы вырастут.** Сейчас `grep` сканирует файл целиком. Для логов
до нескольких гигабайт с `LC_ALL=C` это доли секунды и приемлемо. Если объёмы
станут заметно больше, правильный следующий шаг — двоичный поиск по смещению
в файле: логи упорядочены по времени, и нужный участок находится за O(log n)
вместо полного прохода. Готовые инструменты:
[timegrep](https://github.com/linux-wizard/timegrep),
[brep](https://pypi.org/project/brep),
[log_slice](https://github.com/joelplane/log_slice/). Сейчас это не сделано
намеренно: усложнение без выигрыша на текущих объёмах.

**Безопасность.** Команды собираются только в коде и экранируются через
`shlex.quote`. Текст пользователя попадает лишь как фиксированная строка
поиска (`grep -F`), не как регулярное выражение и не как часть команды.
Выполняются только `find`, `grep`/`zgrep`, `tail`, `date`.

### API и Swagger

Описание всех методов публикуется агентом и **доступно без входа** — иначе
внешняя система не узнает формат запросов. Сами методы при этом закрыты.

```
http://MONITORING_IP:5001/docs          Swagger UI
http://MONITORING_IP:5001/redoc         ReDoc
http://MONITORING_IP:5001/openapi.json  спецификация
```

Методы сгруппированы по разделам: События, Чат, Метрики, Диагностика,
Кластеры, Доступ, Служебное.

Зарегистрировать событие извне (Zabbix и подобные) — токен, cookie не нужна:

```bash
curl -X POST http://MONITORING_IP:5001/api/alerts/ingest      -H 'X-API-Key: ТОКЕН' -H 'Content-Type: application/json'      -d '{"alert":"Disk low","severity":"critical","cluster":"kemerovo"}'
```

Спросить агента программно:

```bash
curl -X POST http://MONITORING_IP:5001/chat      -H 'Content-Type: application/json'      -d '{"message":"что с Кемерово за последний час?"}'
```

### Инструменты вместо ключевых слов

Раньше агент решал по словам в вопросе, что подложить в контекст, — и список
слов приходилось расширять после каждой новой формулировки. Если ваш LLM
поддерживает function calling, модель **сама запрашивает** нужное:
`get_current_metrics`, `get_history`, `get_breakdown`, `run_diagnostics`,
`run_sql`, `read_logs`, `get_alerts`.

```bash
LLM_TOOLS="auto"        # auto — проверить и включить, on — принудительно, off — выключить
LLM_TOOL_ROUNDS=3       # сколько раундов дозапросов разрешено
```

При `auto` делается один пробный запрос. Не поддерживается — агент работает
по-старому, ключевыми словами. Какие инструменты были вызваны, видно чипом
рядом с ответом.

Окно инструмента ограничено тем же потолком `MAX_METRICS_HOURS`: модель не
сможет запросить неделю сырых данных.

### Сравнение с обычным днём

К истории добавляется тот же период **неделю назад** (`offset 7d`, тот же день
недели и час — по будням и выходным профиль разный). Без базы «QPS 1200»
ничего не значит, и модель вынуждена гадать; с ней получается «вдвое выше
обычного».

Настраивается `BASELINE_OFFSET_DAYS` (по умолчанию 7).

### Планы выполнения и схемы таблиц

При диагностике для 3 самых дорогих SELECT выполняется `EXPLAIN`, а для таблиц
из плана — `SHOW CREATE TABLE`. Ответ превращается из «запрос медленный»
в «полное сканирование `orders`, нет индекса по `(created, status)`».

В `DIGEST_TEXT` вместо значений стоят `?`; для плана подставляется `1`.
Запросы, для которых `EXPLAIN` не проходит, пропускаются — это ожидаемо.

### Расхождения конфигурации primary и replica

Сравниваются ключевые параметры (`innodb_buffer_pool_size`, `sync_binlog`,
`long_query_time`, `sql_mode` и другие). Разные настройки на серверах одного
кластера — частая причина того, что реплика ведёт себя иначе при той же
нагрузке. Часть расхождений нормальна (`read_only`), остальные агент объясняет.

### Лента событий

Алерты и события сводятся в одну ленту по времени, чтобы причинно-следственная
связь была видна сразу, а не собиралась мысленно из разных блоков.

### Оценка ответов

Под каждым ответом — «Ответ помог? да / нет», при отказе можно оставить
комментарий. Вопрос, ответ и оценка сохраняются.

```bash
curl -s http://localhost:5001/api/feedback/stats?days=30 | python3 -m json.tool
```

Через месяц видно, на каких вопросах агент систематически промахивается.
Без этого улучшения делаются вслепую.

### Диагностика БД

По просьбе «продиагностируй», «почему медленно», «найди узкое место» агент
**сам выполняет** набор запросов Performance Schema на каждом сервере кластера
и разбирает результаты. Советовать «посмотрите performance_schema»
бессмысленно, если можно просто посмотреть.

Набор собран по методике из документации MySQL:

| Проверка | Что показывает |
|----------|----------------|
| Самые тяжёлые запросы | куда реально уходит время — по суммарному, а не по числу вызовов |
| Полное сканирование таблиц | нехватка индексов, самая частая причина роста нагрузки |
| Активные сессии | долгие и подвисшие запросы прямо сейчас |
| Ожидания по типам событий | различает упор в диск, блокировки и сеть |
| Таблицы по вводу-выводу | какие таблицы греют диск |
| Файлы по вводу-выводу | подтверждает или опровергает упор в диск |
| Ожидания блокировок | кто кого блокирует (нужен `sys`) |
| Неиспользуемые индексы | замедляют запись, занимают память (нужен `sys`) |
| Подключения и потоки | упор в `max_connections`, отказы |
| Состояние InnoDB | буферный пул, ожидания строк, дедлоки (нужен `PROCESS`) |

Запросы, для которых нет прав или представлений `sys`, **пропускаются молча** —
иначе половина отчёта состояла бы из сообщений об отказе. В промпте есть
требование сказать, каких прав не хватило.

Все запросы проходят тот же валидатор «только чтение», что и запросы
пользователя.

```bash
curl -s http://localhost:5001/api/diagnose/kemerovo | python3 -m json.tool
curl -s 'http://localhost:5001/api/diagnose/kemerovo?keys=top_queries,full_scans'
```

Методика разбора задана в системном промпте (правило 11): есть ли проблема →
куда уходит время → почему запросы тяжёлые → упирается ли в ресурсы сервера →
что конкретно делать. С опорой на собранные цифры, а не на общие советы.

Источники методики: [MySQL: Using the Performance Schema to Diagnose
Problems](https://dev.mysql.com/doc/refman/8.0/en/performance-schema-examples.html),
[MinervaDB: MySQL Performance Troubleshooting](https://minervadb.com/mysql-performance-troubleshooting-best-practices-and-optimization-techniques/),
[Severalnines: Identify MySQL Performance Issues](https://severalnines.com/blog/how-identify-mysql-performance-issues-slow-queries/).

### SQL-запросы к кластерам

Агент может **читать** данные из БД: выполнить запрос, который вы написали
в чате, и разобрать результат вместе с метриками.

Учётка задаётся у кластера в [clusters.json](clusters.json) — **одна на все
серверы кластера**, спрашивается в `./manage_cluster.sh add`:

```json
{
  "name": "kemerovo",
  "db_user": "ai_agent",
  "db_password": "...",
  ...
}
```

Пусто — запросы для этого кластера отключены.

**Три режима подключения.** Задаются полем `db_via_ssh` у кластера:

```json
"db_via_ssh": "tunnel"
```

| | `direct` (по умолчанию) | `tunnel` | `exec` |
|---|---|---|---|
| Как работает | TCP на 3306 сервера | SSH пробрасывает локальный порт на 3306 | по SSH клиентом `mysql` на сервере |
| Порт 3306 наружу | нужен | **не нужен** | **не нужен** |
| Учётка MySQL | `'ai_agent'@'<IP мониторинга>'` | `'ai_agent'@'localhost'` | `'ai_agent'@'localhost'` |
| Клиент `mysql` на сервере | не нужен | **не нужен** | нужен |
| Типы значений | родные типы MySQL | родные типы MySQL | текст из TSV |
| Зависимости агента | `pymysql` + `cryptography` | `pymysql` + `cryptography` | нет |

### Логи в несколько гигабайт

Лог приложения на 17 ГБ обычным `grep` читается минутами и не укладывается
ни в какой разумный таймаут — а записи за нужный час занимают в нём
мегабайты. Помогает то, что лог отсортирован по времени: файл можно не
читать подряд, а делить пополам, как отсортированный массив.

Агент берёт блок в середине файла, достаёт из него первую строку с датой и
сравнивает с искомой — половина файла отбрасывается. Семнадцать гигабайт
сходятся к нужному месту примерно за семнадцать таких проб: пара мегабайт
чтения вместо семнадцати гигабайт. Весь поиск идёт **одной** командой на
самом сервере — гонять пробы по одной через SSH означало бы семнадцать
сетевых задержек вместо одной.

В отчёте видно, чем всё кончилось:

```
### Логи приложения 10.0.0.7
  Просмотрено файлов: 2 из 14 (выбраны по времени изменения)
  /var/log/lanbilling/core.log — 17.0 ГБ, изменён 2026-09-09 16:40 ·
      просмотрено 48 МБ из 17.0 ГБ — нужный кусок найден делением файла
```

Разбор даты понимает ISO (`2026-09-07`), формат Lanbilling (`07.09.2026`),
`07/09/2026` и `# Time: 260907` из slow-лога MySQL 5.6. Строка без даты
поиск не ломает: такая проба считается «раньше искомого», и граница просто
уезжает ближе к началу файла — прочитаем лишнее, но нужное не потеряем.

Что осталось как было:

- **порог** — деление включается с 256 МБ; на файле поменьше обычный `grep`
  отработает быстрее, чем три десятка проб;
- **архивы `.gz`** — в них нет соответствия «смещение ↔ время», поэтому
  сжатые файлы по-прежнему читаются `zgrep` целиком;
- **результат** — тот же, что дал бы полный проход: внутри найденного куска
  всё равно работает тот же `grep` по датам.

Файлы одного запроса читаются параллельно, а не по очереди: это независимые
команды на одном сервере, и складывать их таймауты незачем.

**Туннель** — середина между двумя крайностями: порт наружу открывать не надо,
но и ставить клиент `mysql` на сервер БД не требуется, а значения приходят
типами MySQL, а не разобранным текстом. Поднимается на время запроса и
закрывается сразу после: держать постоянный проброс значит следить за его
живостью и чинить обрывы, а выигрыш — доли секунды.

Для `tunnel` и `exec` нужен тот же SSH-доступ, что и для чтения логов
(`SSH_USER` в `config.env`). MySQL в обоих случаях видит подключение как
пришедшее с самого сервера, поэтому учётке хватает `@'localhost'`.

Пароль передаётся переменной окружения `MYSQL_PWD`, а не аргументом
командной строки — иначе его увидел бы любой пользователь сервера через `ps`.
Если `db_user` не заполнен, но режим SSH включён, используются настройки
`~/.my.cnf` той учётки, под которой заходим — пароль тогда вообще не покидает
сервер.

Глобальное значение по умолчанию — переменная `DB_VIA_SSH` в `config.env`.
Старое `"db_via_ssh": true` продолжает работать и означает `exec`.

**Права: нужен только SELECT.** На каждом сервере кластера (primary и replica):

```sql
-- при подключении напрямую
CREATE USER 'ai_agent'@'<IP_сервера_мониторинга>' IDENTIFIED BY 'пароль';
GRANT SELECT ON *.* TO 'ai_agent'@'<IP_сервера_мониторинга>';

-- при db_via_ssh: "tunnel" или "exec" — запрос приходит с самого сервера
CREATE USER 'ai_agent'@'localhost' IDENTIFIED BY 'пароль';
GRANT SELECT ON *.* TO 'ai_agent'@'localhost';

FLUSH PRIVILEGES;
```

`SELECT ON *.*` покрывает и `information_schema`, и `performance_schema`, и
`sys` — отдельные гранты на них не нужны.

Представления `sys` выполняются с правами их владельца (`DEFINER = mysql.sys`),
поэтому дополнительных прав они не требуют. Если `sys` в вашей сборке нет или
она не установлена, проверки на ней просто пропускаются с объяснением — всё
остальное работает.

Два необязательных права, если нужна полная диагностика:

| Право | Что даёт | Без него |
|-------|----------|----------|
| `PROCESS` | `SHOW PROCESSLIST` со **всеми** сессиями, `SHOW ENGINE INNODB STATUS`, `EXPLAIN FOR CONNECTION` для чужого соединения | видны только свои сессии, INNODB STATUS недоступен, план идущего запроса не получить |
| `REPLICATION CLIENT` | `SHOW SLAVE STATUS` | статус репликации через SQL недоступен (метрики Prometheus при этом работают) |
| `SHOW VIEW` | `EXPLAIN` для запросов через представления | сервер отвечает «lacking privileges for underlying table» |

```sql
GRANT PROCESS, REPLICATION CLIENT ON *.* TO 'ai_agent'@'<IP>';
```

Права на запись не нужны **ни при каких обстоятельствах** — агент их не
использует и не может использовать.

**Как ограничено чтение.** Запрос проверяется до отправки в БД:

- разрешены только `SELECT`, `SHOW`, `EXPLAIN`, `DESCRIBE`, `WITH`;
- одна инструкция — `;` внутри запроса отклоняется, чтобы не подставили вторую;
- запрещены `INSERT`/`UPDATE`/`DELETE`/`DROP`/`GRANT`/`SET`/`CALL`/`KILL`,
  запись в файл (`OUTFILE`, `DUMPFILE`);
- **исполняемые комментарии MySQL `/*! … */` отклоняются целиком** — MySQL их
  выполняет, и через них прячется что угодно;
- автоматически дописывается `LIMIT` (`SQL_MAX_ROWS`, 200);
- на сессию ставится `TRANSACTION READ ONLY` и `MAX_EXECUTION_TIME`
  (`SQL_TIMEOUT_S`, 15 с) — страховка на стороне сервера.

**Версия MySQL спрашивается на старте** у каждого кластера и кладётся
в системный промпт. Без этого агент советовал синтаксис наугад: у 5.7 и 8.0
разные таблицы `performance_schema` и разный `SHOW`.

```bash
curl -s http://localhost:5001/api/db/versions | python3 -m json.tool
```

Запрос из чата — просто напишите его:

```
выполни SELECT count(*) FROM orders WHERE created > now() - interval 1 day по Кемерово
посмотри ```sql
SHOW ENGINE INNODB STATUS
``` и объясни
```

Или через API (нужны права администратора):

```bash
curl -X POST http://localhost:5001/api/query      -H 'Content-Type: application/json'      -d '{"cluster":"kemerovo","sql":"SHOW PROCESSLIST"}'
```

### Проверка сертификатов в pip отключена

`install_agent.sh` всегда передаёт `--trusted-host` для всех используемых
хостов: вашего репозитория из `PIP_INDEX_URL`, `extra-index`, а также
`pypi.org` и `files.pythonhosted.org`. То же пишется в `venv/pip.conf`, чтобы
последующие ручные `pip install` в этом venv не спотыкались.

За корпоративным TLS-прокси сертификат подменяется, и без этого pip падает
на проверке. Обратная сторона очевидна: подлинность репозитория не
проверяется — полагаемся на то, что трафик не покидает периметр. Если такое
не подходит, укажите свой CA в `PIP_CERT` и уберите `--trusted-host` из
скрипта.

Нужен пакет `pymysql` — `install_agent.sh` ставит его сам, **только если**
хотя бы у одного кластера заполнен `db_user`. Пакет на чистом Python, без
системных библиотек — в закрытый pip-репозиторий ложится без проблем.

Вместе с ним ставится **`cryptography`**: MySQL 8.0 по умолчанию заводит
учётки с плагином `caching_sha2_password`, а драйвер без этого пакета такое
подключение не поднимает и отвечает `Authentication plugin
'caching_sha2_password' requires the cryptography package`. Сообщение звучит
как проблема сервера, хотя чинится на стороне агента, поэтому агент к нему
добавляет разбор и команду для исправления. То же касается `asyncmy`, когда
хранилище самого агента переведено на MySQL, — пакет ставится и там.

В отличие от `pymysql`, у `cryptography` бинарные колёса, и на старом Python
нужной версии может не оказаться: скрипт сначала пробует закреплённую
`42.0.8`, потом — любую подходящую интерпретатору. Если пакета нет во
внутреннем индексе pip совсем, оставшийся выход — перевести учётку агента на
прежний плагин:

```sql
ALTER USER 'ai_agent'@'%' IDENTIFIED WITH mysql_native_password BY 'пароль';
```

### Откуда числа в «Запасе по ресурсам»

Раздел долго показывал «заметного роста нет» по дискам и «метрик соединений
нет» по подключениям — при исправном экспортёре. Причина оказалась не в
мониторинге: `prom_query` отдаёт **одно** число, а код разбирал ответ как
словарь рядов. Условие `isinstance(avail, dict)` не выполнялось никогда,
поэтому диски пропускались молча, а соединения объявлялись отсутствующими.

Теперь есть `prom_query_map` — все ряды ответа с разбором по метке. Дискам
это принципиально: файловых систем на сервере с десяток, и «первая
попавшаяся» — не ответ.

Соединения считаются по `mysql_global_status_threads_connected`, которую
отдаёт любая сборка экспортёра, а не по `max_used_connections`: последнюю
отдают не все, и это отметка максимума с запуска сервера — темп роста по
ней получался ложный. Пик берётся как `max_over_time` за неделю (упираемся
мы именно в пики), рост — разница с таким же окном неделю назад.

**Если метрик нет совсем**, агент не сдаётся: числа лежат в самой базе, и
учётка для них у него уже есть. `Threads_connected`, `Max_used_connections` и
`@@max_connections` спрашиваются напрямую, а в отчёте честно написано «пик с
запуска сервера» вместо «пик за неделю» — сравнивать их между собой нельзя.

**Если и база недоступна**, в ответе будет не «данных нет», а конкретная
причина — они разные и чинятся по-разному:

| Что видит агент | Что написано в отчёте |
|---|---|
| цели нет в Prometheus | «проверьте, что кластер применён: `manage_cluster.sh apply`» |
| цель есть, `up=0` | «экспортёр не отвечает: `systemctl status mysqld_exporter`» |
| экспортёр отвечает, метрик `mysql_global_status_*` нет | «запущен без `--collect.global_status` — поправьте ExecStart» |
| нет только `max_connections` | «нужен `--collect.global_variables`, либо заполните `db_user`» |

### Одна работа на всех

Диагностика стоит дорого: профиль нагрузки — это два среза
`performance_schema` с паузой между ними, разбор настроек — сотни строк по
SSH, самопроверка — обход всех серверов. Раньше каждый запрос выполнялся сам
по себе: двое дежурных открыли страницу кластера одновременно — сервер снял
профиль дважды, нагрузив базу вдвое ради одинакового ответа.

Теперь работа привязана к тому, **что** просят, а не к тому, **кто** просит.
Первый пришедший запускает её, остальные подключаются к той же задаче и
получают тот же результат. Свежий результат недолго держится в памяти:
обновление страницы или переход между вкладками не снимают те же метрики
заново.

Второе свойство важнее первого: **задача не отменяется вместе с запросом**.
Закрытая вкладка больше не выбрасывает почти доделанную работу — она дойдёт
до конца, положит результат в память, и следующий, кто спросит, получит его
сразу.

| Что | Сколько результат считается свежим |
|---|---|
| репликация | 20 с |
| профиль нагрузки, готовность к обслуживанию | 30 с |
| диагностика, аномалии, самопроверка, чтение логов | 60 с |
| запас ресурсов, разбор настроек | 2 мин |
| рост данных, копии, история настроек | 5 мин |
| дублирующие индексы | 10 мин |

Реестр живёт в памяти процесса: перезапуск агента его очищает, и это
правильно — после рестарта данные всё равно надо снимать заново.

### Остановка генерации

Пока агент отвечает, кнопка отправки заменяется на **■** — она прерывает
генерацию. Уже написанная часть ответа сохраняется в истории с пометкой
`[генерация остановлена]`: пользователь её видел, и в следующем вопросе может
на неё ссылаться.

Технически: раньше сервер во время стриминга не читал сокет и «стоп» бы просто
не услышал. Теперь чтение вынесено в отдельную задачу — служебные сообщения
(`ping`, `stop`) разбираются сразу, вопросы кладутся в очередь.

### Хранение истории алертов

Алерты вместе с разбором от LLM пишутся в **SQLite** — `/opt/ai-alert-agent/alerts.db`
(модуль `sqlite3` из стандартной библиотеки, дополнительных pip-пакетов не нужно).
История переживает рестарт агента; записи старше окна хранения удаляются
автоматически при следующей записи.

```bash
ALERTS_RETENTION_DAYS=30      # config.env, спрашивается в ./configure.sh
```

```bash
curl -s http://localhost:5001/alerts/history?limit=5 | python3 -m json.tool
# {
#   "total": 42,              ← всего за окно хранения
#   "items": [...],           ← последние limit, новые сверху
#   "retention_days": 30,
#   "persistent": true        ← false = БД недоступна, история только в памяти
# }
```

Если `persistent: false` — агент не смог открыть БД (обычно права на
`/opt/ai-alert-agent`) и работает на резервной копии в памяти: последние
200 записей, теряются при рестарте. Причина пишется в лог:
```bash
journalctl -u ai-alert-agent | grep -i "хранилище алертов"
```

Посмотреть напрямую:
```bash
sqlite3 /opt/ai-alert-agent/alerts.db \
  "SELECT ts, alert, cluster_label, severity FROM alerts ORDER BY ts DESC LIMIT 10;"
```

Метрики Prometheus хранятся независимо — `PROMETHEUS_RETENTION` (по умолчанию
`30d`), каталог `/var/lib/prometheus`.

## HTTPS / WSS через nginx

Для продакшна поставьте nginx перед агентом:

```nginx
server {
    listen 443 ssl;
    server_name dba-ai.company.ru;

    ssl_certificate     /etc/pki/tls/certs/your.crt;
    ssl_certificate_key /etc/pki/tls/private/your.key;

    location / {
        proxy_pass http://127.0.0.1:5001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # WebSocket — обязательны эти три строки
    location /ws {
        proxy_pass http://127.0.0.1:5001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 300s;     # стриминг длинных ответов
    }
}
```

Фронтенд определяет протокол автоматически: на `https://` странице откроет `wss://`.

### Агент на подпути (`/ai-agent/`)

Если агент живёт не в корне, укажите подпуть в `./configure.sh`
(секция «Обратный прокси») — он попадёт в `.env` агента и страница начнёт
строить свои ссылки от него. Там же рядом спрашиваются подпути для Prometheus
и Alertmanager — все три задаются одинаково, одним путём.

```bash
ROOT_PATH="/ai-agent"      # в config.env
sudo ./scripts/install_agent.sh
```

```nginx
# без слэша на конце — иначе /ai-agent отдаст 404 мимо location ниже
location = /ai-agent { return 301 /ai-agent/; }

location /ai-agent/ {
    proxy_pass http://127.0.0.1:5001/;    # ← слэш обязателен: срезает префикс
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}

location /ai-agent/ws {
    proxy_pass http://127.0.0.1:5001/ws;  # ← явный путь, тоже без префикса
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 300s;
}
```

Как это работает: **префикс срезает nginx**, внутри агента маршруты остаются
без него (`/clusters`, `/ws`, `/static/...`). `ROOT_PATH` нужен только для того,
чтобы агент подставил в страницу `<base href="/ai-agent/">` — от него
браузер и достраивает все относительные адреса.

### Prometheus и Alertmanager на подпутях

Задаются ровно так же, как подпуть агента — одним путём в той же секции
мастера:

```bash
PROMETHEUS_ROOT_PATH="/prometheus"
ALERTMANAGER_ROOT_PATH="/alertmanager"
```

Этого достаточно: сервисы начнут отдаваться под своим префиксом, а скрипты
выведут из него все внутренние адреса.

**Внешний адрес — необязательное дополнение.** Он нужен только чтобы ссылки
*в самих алертах* (`generatorURL`, ссылка на silence) вели наружу, а не на
`localhost`. Мастер спрашивает его следом, Enter — пропустить:

```bash
EXTERNAL_BASE_URL="https://monitor.company.ru"
# → PROMETHEUS_EXTERNAL_URL="https://monitor.company.ru/prometheus"
# → ALERTMANAGER_EXTERNAL_URL="https://monitor.company.ru/alertmanager"
```

`install_monitoring.sh` добавит в systemd-юниты:

```
# только подпуть:
--web.route-prefix=/prometheus/
# подпуть + внешний адрес:
--web.external-url=https://monitor.company.ru/prometheus --web.route-prefix=/prometheus/
```

**Сервисы отдают себя под своим путём**, а не в корне. Поэтому nginx префикс
**не срезает** — `proxy_pass` без завершающего слэша:

```nginx
location /prometheus/ {
    proxy_pass http://127.0.0.1:9090;       # БЕЗ слэша — путь идёт как есть
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location /alertmanager/ {
    proxy_pass http://127.0.0.1:9093;       # БЕЗ слэша
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

> Это отличается от агента: тот отвечает в корне, и там `proxy_pass` **со**
> слэшем. Prometheus и Alertmanager умеют работать под префиксом сами, поэтому
> проще отдать им путь целиком.

Следствие: **все внутренние адреса тоже содержат префикс**. Скрипты выводят их
из `PROMETHEUS_ROOT_PATH` / `ALERTMANAGER_ROOT_PATH` автоматически:

| Что | Адрес при `PROMETHEUS_ROOT_PATH="/prometheus"` |
|-----|-----------------------------------------------|
| Собственный scrape-таргет | `metrics_path: '/prometheus/metrics'` в job `prometheus` |
| Датасорс Grafana | `http://localhost:9090/prometheus` |
| `PROMETHEUS_URL` агента | `http://localhost:9090/prometheus` |
| Перезагрузка конфига | `POST http://localhost:9090/prometheus/-/reload` |
| Alertmanager в `prometheus.yml` | `path_prefix: '/alertmanager/'` в блоке `alerting` |

Пустые значения дают прежнее поведение — всё в корне, без префиксов.

⚠️ `prometheus.yml` **полностью перегенерируется** командой `apply`, поэтому
править `metrics_path` в нём руками бесполезно: значение берётся из
`PROMETHEUS_ROOT_PATH` в `config.env`.

Применить к уже установленному стеку:

```bash
sudo ./scripts/install_monitoring.sh    # юниты, датасорс, базовый конфиг
sudo ./manage_cluster.sh apply          # prometheus.yml с metrics_path
sudo ./scripts/install_agent.sh         # PROMETHEUS_URL агента
```

**Внутренние обращения тоже идут через nginx — без порта.** Раз подпути уже
настроены в nginx, скрипты обращаются к сервисам по `http://localhost/prometheus`,
а не `http://localhost:9090/prometheus`. Это касается датасорса Grafana,
`PROMETHEUS_URL` агента, health-проверок, перезагрузки конфига и целей скрейпа
(`targets: ['localhost']`). Хост настраивается переменной `INTERNAL_BASE_URL`
в `config.env` (по умолчанию `http://localhost`).

Без подпутей маршрутизировать в nginx не по чему, поэтому используется прямой
адрес с портом — прежнее поведение.

⚠️ Следствие: **nginx должен работать и знать про эти location до запуска
скриптов.** Иначе health-проверки не пройдут — сервис живой, но по адресу
через nginx недоступен.

Alertmanager шлёт вебхуки агенту на `localhost:${AGENT_PORT}/webhook` — этот
адрес от префиксов не зависит. Порты 9090/9093 можно закрыть в firewalld.

Две самые частые ошибки:

| Симптом | Причина |
|---------|---------|
| `{"detail":"Not Found"}` на самой странице | `proxy_pass` **без** завершающего слэша — агент получает `/ai-agent/`, а такого маршрута у него нет |
| Страница открылась, но пустая и белая; в консоли 404 на `app.js` | `ROOT_PATH` не задан — `<base>` остался `/`, и браузер ищет статику в корне сайта |

Проверить, что подставилось:

```bash
curl -s http://localhost:5001/ | grep '<base'
#   <base href="/ai-agent/">
```

## Аутентификация

Веб-интерфейс закрыт формой входа на `/login`. Настраивается в `./configure.sh`
(секция 10). Источники проверяются по очереди: **SSO → LDAP → локальный админ**,
любой можно выключить.

### Локальный администратор

Пароль хранится только хешем PBKDF2-SHA256 (200 000 итераций, случайная соль) —
в `config.env` и `.env` агента открытого пароля нет:

```bash
AUTH_ENABLED="true"
AUTH_ADMIN_USER="admin"
AUTH_ADMIN_PASSWORD_HASH="pbkdf2_sha256$200000$<соль>$<хеш>"
AUTH_SECRET="<64 hex>"          # подписывает сессионные cookie
AUTH_SESSION_TTL_HOURS=12
```

Сессия — подписанный HMAC cookie (`HttpOnly`, `SameSite=Lax`), состояние на
сервере не хранится. `AUTH_SECRET` генерируется один раз и сохраняется: если его
сменить, все сессии станут недействительны.

Смена пароля: `./configure.sh` → секция 10 → новый пароль → `sudo ./scripts/install_agent.sh`.

### LDAP / Active Directory

```bash
LDAP_ENABLED="true"
LDAP_URL="ldaps://dc.company.ru:636"
LDAP_BIND_TEMPLATE="{username}@company.ru"        # для AD обычно UPN
LDAP_BASE_DN="DC=company,DC=ru"                   # нужен только для проверки группы
LDAP_USER_FILTER="(sAMAccountName={username})"
LDAP_TLS_VERIFY="true"

# Группы, членам которых разрешён вход. Несколько — через «;»
# (в DN есть запятые, поэтому разделитель другой).
LDAP_ALLOWED_GROUPS="CN=DBA,OU=Groups,DC=company,DC=ru;CN=Monitoring,OU=Groups,DC=company,DC=ru"
LDAP_NESTED_GROUPS="true"
```

Проверка — обычный bind учётными данными пользователя; пароль нигде не
сохраняется.

**Импорт из nslcd.** Если на сервере уже настроен `nslcd`, параметры
подключения можно не переписывать руками — легко ошибиться в DN:

```bash
sudo ./scripts/import_nslcd.py                      # предпросмотр
sudo ./scripts/import_nslcd.py --write      --groups 'CN=DBA,OU=Groups,DC=company,DC=ru;CN=Ops,OU=Groups,DC=company,DC=ru'
```

Скрипт заполняет всё, кроме групп доступа — их указываете вы:

| `nslcd.conf` | `config.env` |
|--------------|--------------|
| `uri` | `LDAP_URL` (берётся первый адрес) |
| `base` | `LDAP_BASE_DN` |
| `binddn` / `bindpw` | `LDAP_SEARCH_USER` / `LDAP_SEARCH_PASSWORD` |
| `filter passwd` + `map passwd uid` | `LDAP_USER_FILTER` с подстановкой `{username}` |
| `tls_reqcert` | `LDAP_TLS_VERIFY` (`never`/`allow` → `false`) |
| `bind_timelimit` | `LDAP_TIMEOUT` |

`LDAP_BIND_TEMPLATE` собирается как UPN `{username}@домен` из `base DN`.
В самом `nslcd` такого шаблона нет — он ищет DN сервисной учёткой, — а нам он
нужен для проверки пароля пользователя.

Атрибут имени входа берётся из `map passwd uid`, а если его нет — по типу
каталога: `sAMAccountName` для AD, `uid` для OpenLDAP.

Существующие строки в `config.env` заменяются, посторонние не трогаются.

**Доступ по группам.** Заводить вручную каждого из сотен доменных
пользователей нереально, поэтому вход даёт **любой из двух путей**:

1. Явная выдача во вкладке «Доступы».
2. Членство в одной из групп `LDAP_ALLOWED_GROUPS`.

Вошедший по группе автоматически появляется в списке доступов с пометкой
«группа CN=…» — администратор видит, кто зашёл и почему.

⚠️ **Явный отзыв перебивает группу.** Если администратор отозвал доступ,
человек не войдёт, даже оставаясь в разрешённой группе. Иначе отзыв был бы
бессмысленным: при следующем входе доступ восстанавливался бы сам.

`LDAP_NESTED_GROUPS="true"` (по умолчанию) учитывает **вложенные группы** —
через правило AD `1.2.840.113556.1.4.1941`. Без него пользователь, входящий
в разрешённую группу через промежуточную, выглядел бы посторонним, а такая
вложенность в AD встречается постоянно.

**Доступ по netgroup.** Там, где каталог обслуживает ещё и вход на
Linux-серверы через `nslcd`, состав обычно описан не группами AD, а
**netgroup** (`nisNetgroup`). Устроены они принципиально иначе: членство лежит
не в `memberOf` у пользователя, а в самой netgroup — в атрибуте
`nisNetgroupTriple` вида `(хост,пользователь,домен)`, с вложением через
`memberNisNetgroup`. Поэтому проверка групп их не видит, и нужна отдельная.

```bash
# Имена (cn), через «;». Работает вместе с LDAP_ALLOWED_GROUPS: доступ даёт
# любое совпадение — хоть группа AD, хоть netgroup
LDAP_ALLOWED_NETGROUPS="dba;monitoring"
# Своя ветка (в nslcd — строка «base netgroup ...»). Пусто — от LDAP_BASE_DN
LDAP_NETGROUP_BASE="ou=netgroup,dc=company,dc=ru"
LDAP_NETGROUP_FILTER="(objectClass=nisNetgroup)"
```

Не помните имена netgroup — их покажет диагностика, вместе с тем, в каких
состоит конкретный человек:

```bash
sudo ./scripts/ldap_test.py --user ivkop
```

Она же выведет готовую строку `LDAP_ALLOWED_NETGROUPS` для вставки в
`config.env`. Либо прямо из каталога:

```bash
ldapsearch -x -b 'ou=netgroup,dc=company,dc=ru' '(objectClass=nisNetgroup)' cn
```

Вложенные netgroup раскрываются, ссылки по кругу не зацикливают. Пустое поле
пользователя в триплете — например `(-,,)` — по правилам NIS означает
**любой**, то есть вход открыт всем в каталоге; агент такое пропускает, но
пишет предупреждение в лог. Дефис `-` означает «никто».

**Импорт netgroup из nslcd.** Ветка и фильтр берутся автоматически:

```bash
sudo ./scripts/import_nslcd.py --write --netgroups 'dba;monitoring'
```

Заодно исправлено чтение самого `nslcd.conf`: строка `base netgroup ou=...`
задаёт ветку только для этой карты и общий `base` не заменяет — иначе
пользователей искали бы среди netgroup.

**Поиск учётки в каталоге.** Во вкладке «Доступы» есть строка поиска: вводите
фамилию, логин или почту, находите человека и выдаёте доступ кнопкой — руками
логин набирать не нужно. Ищется по `sAMAccountName`, `uid`, `cn`,
`displayName` и `mail`, так что подходит любой из трёх вариантов.

Фильтр собирается **по схеме конкретного сервера**: атрибуты, которых в
каталоге нет, отбрасываются. Жёсткий фильтр под AD ронял поиск в OpenLDAP —
`ldap3` сверяет имена атрибутов со схемой и на `sAMAccountName` выдавал
`LDAPAttributeError: invalid attribute type`. Своё значение можно задать
переменной `LDAP_SEARCH_FILTER` (подстановка `{query}`), тогда оно
используется как есть.

Доступ выдаётся на тот атрибут, по которому проверяется пароль
(`LDAP_USER_FILTER`): `sAMAccountName` в AD, `uid` в OpenLDAP. Иначе доступ
был бы выписан на имя, под которым человек не входит.

Ищется и по **фамилии**: кроме `cn` и `displayName` берутся `sn`, `givenName`
и `gecos`. В posix-каталогах `cn` обычно равен логину, а настоящее ФИО лежит
именно там — без этих атрибутов поиск по фамилии не находил никого.

Условие «это учётная запись человека» берётся из `LDAP_USER_FILTER`, то есть
из строки `filter passwd` вашего `nslcd`: она описывает ровно те объекты,
которые каталог считает пользователями, и это надёжнее догадок про
`objectClass`.

**Настройки берутся из nslcd автоматически.** Пустые значения `LDAP_URL`,
`LDAP_BASE_DN`, `LDAP_USER_FILTER`, `LDAP_BIND_TEMPLATE`, `LDAP_SEARCH_USER`,
`LDAP_SEARCH_PASSWORD` и веток netgroup агент дозаполняет из `/etc/nslcd.conf`
при запуске и пишет в лог, что именно взял. Заполненные в `config.env` не
трогает — явная настройка всегда главнее. Путь задаётся переменной
`NSLCD_CONF`, пустое значение отключает чтение.

**`adminLimitExceeded` — каталог оборвал поиск.** Это не «никого нет», а
«искать так нельзя». Ведущая звёздочка в `(атрибут=*текст*)` отключает индекс:
серверу приходится перебирать всю ветку, и он прекращает работу по
административному лимиту. Поэтому по умолчанию ищем **по началу строки**
(`LDAP_SEARCH_MODE="prefix"`) — для фамилии и логина этого достаточно.
Поиск по вхождению включается явно:

```bash
LDAP_SEARCH_MODE="contains"
```

Второе средство — **сузить ветку**. В `nslcd` люди лежат в отдельной ветке
(строка `base passwd`), и она заметно уже общей:

```bash
LDAP_USER_BASE="ou=people,dc=company,dc=ru"
```

Импорт из nslcd подставляет её автоматически. Если и это не помогает, задайте
`LDAP_SEARCH_FILTER` по атрибуту, который в каталоге проиндексирован.

Коды `timeLimitExceeded`, `sizeLimitExceeded` и `adminLimitExceeded`
расшифровываются и в интерфейсе, и в логе — вместе с тем, что делать.

**Почему поиск ничего не находит.** Точный ответ даёт диагностика — она
повторяет ровно тот запрос, который делает агент:

```bash
sudo ./scripts/ldap_test.py --user ivkop --search Иванов
```

Выводятся база, прочитана ли схема, список атрибутов, готовый фильтр, код
ответа каталога и число записей. Если ничего не нашлось, тот же поиск
повторяется без условия по `objectClass`: нашлось — значит мешает условие, и
скрипт печатает готовую строку `LDAP_SEARCH_FILTER`; не нашлось — дело в базе
поиска или в самом запросе. То же самое агент пишет в свой лог:

```bash
journalctl -u ai-alert-agent | grep 'Поиск в каталоге'
```

⚠️ **Скрипт находит, а агент нет** — почти всегда потому, что `config.env`
поправили, а установку не перезапускали: скрипт читает `config.env`, агент —
свой `/opt/ai-alert-agent/.env`. Диагностика теперь сверяет оба файла и
показывает расхождения построчно. Лечится `sudo ./scripts/install_agent.sh`.

Проверка групп по `memberOf` пропускается, если такого атрибута в схеме нет —
в OpenLDAP его даёт overlay `memberof`, и он включён не всегда. В логе об этом
пишется прямо, с указанием использовать `LDAP_ALLOWED_NETGROUPS`.

Читать каталог агент может двумя способами. Если `LDAP_SEARCH_USER` не задан —
**анонимно**, ровно как это делает `nslcd` без `binddn`: во многих каталогах
чтение открыто всем, и требовать учётку значило бы запрещать то, что каталог
разрешает. Если анонимное чтение закрыто, поиск так и скажет — тогда заводится
сервисная учётка:

```bash
LDAP_SEARCH_USER="CN=svc-ldap,OU=Service,DC=company,DC=ru"
LDAP_SEARCH_PASSWORD="..."
```

Прав достаточно самых обычных — чтение каталога, писать ничего не нужно.

В результатах поиска у каждого человека — **выбор роли** (пользователь или
администратор) и кнопка «Выдать доступ». Список листается по 10 записей,
внизу видно, сколько найдено всего. **Enter** в строке поиска работает как
кнопка «Найти», в форме ручной выдачи — как «Выдать доступ».

После выдачи страница результатов не сбрасывается: запись помечается «уже
выдан» на месте, и можно продолжать с того же места.
Пользовательский bind здесь не подходит принципиально: доступ выдаётся **до**
первого входа человека, и его пароля у нас ещё нет.

Строка поиска всегда на месте; если каталог недоступен, она неактивна и прямо
называет причину. Выдать доступ по логину вручную можно всегда — форма под
поиском, она же нужна для SSO и OIDC.

Ищутся оба варианта имени входа: `sAMAccountName` в AD и `uid` в OpenLDAP.
Выдаётся доступ на тот атрибут, по которому идёт проверка пароля
(`LDAP_USER_FILTER`), — иначе доступ был бы выписан на имя, под которым
человек не входит.

Проверка групп работает и для SSO с OIDC — там пароля пользователя нет,
поэтому поиск идёт сервисной учёткой `LDAP_SEARCH_USER`.

Членство проверяется **при входе**, а не на каждом запросе: сессия
сверяется с локальным списком доступов, поэтому в каталог не ходим по сто
раз в минуту. Отзыв при этом действует немедленно.

Старое поле `LDAP_REQUIRED_GROUP` продолжает работать — оно добавляется
в список как одна из групп.

Нужен пакет `ldap3` — `install_agent.sh` ставит его сам, но **только когда
`LDAP_ENABLED=true`**. В закрытом контуре он должен быть в вашем
`PIP_INDEX_URL`; если установка не удалась, скрипт скажет об этом явно, и вход
по LDAP работать не будет (локальный админ продолжит работать).

### SSO через обратный прокси

Рассчитано на типовую корпоративную схему: nginx с Kerberos/SAML/oauth2-proxy
аутентифицирует пользователя и передаёт имя заголовком.

```bash
SSO_ENABLED="true"
SSO_HEADER="X-Remote-User"
SSO_TRUSTED_PROXIES="127.0.0.1,::1"      # адреса, чьему заголовку верим
SSO_LOGOUT_URL="https://sso.company.ru/logout"
```

```nginx
location /ai-agent/ {
    auth_gss on;                          # или auth_request к oauth2-proxy
    proxy_pass http://127.0.0.1:5001/;
    proxy_set_header X-Remote-User $remote_user;
}
```

⚠️ **`SSO_TRUSTED_PROXIES` — не формальность.** Заголовок принимается только от
перечисленных адресов. Без этой проверки любой, кто достучится до порта агента
напрямую, поставил бы себе `X-Remote-User: admin`. Поэтому при включённом SSO
порт `5001` должен быть закрыт снаружи — доступ только через nginx.

### Список доступов

**Учётной записи в домене недостаточно.** После успешной проверки пароля
(LDAP), заголовка SSO или токена OIDC агент дополнительно смотрит, выдан ли
пользователю доступ. Не выдан — вход отклоняется с понятным сообщением, а не
«неверный пароль».

Исключение одно: **локальный администратор**. Это bootstrap-учётка, которой
список и наполняют, поэтому она в нём не нуждается.

Управление — вкладка **🔑 Доступы** (видна только администраторам):

- **Поиск по каталогу.** Введите фамилию, логин или почту — агент ищет в AD и
  показывает найденных. Кнопка «Выдать доступ» добавляет выбранного, вводить
  логин руками не нужно. Требуется сервисная учётная запись:
  ```bash
  LDAP_SEARCH_USER="CN=svc-monitor,OU=Service,DC=company,DC=ru"
  LDAP_SEARCH_PASSWORD="..."
  LDAP_BASE_DN="DC=company,DC=ru"
  ```
  Пользовательский bind тут не подходит: доступ выдают **до** того, как человек
  впервые вошёл.
- **Добавление по логину вручную** — для SSO/OIDC, когда поиска по каталогу нет.
- **Роль** `user` или `admin`. Админ дополнительно управляет доступами.
- **Отзыв** — мягкий: запись остаётся со статусом «отозван», чтобы был виден
  факт выдачи и отзыва. Кнопка «Вернуть» восстанавливает.

Логины приводятся к единому виду: `COMPANY\J.Smith`, `J.Smith` и `j.smith` —
одна и та же учётная запись.

**Отзыв действует немедленно.** Каждый запрос перепроверяет список, поэтому уже
выданная сессионная cookie перестаёт работать сразу, а не после истечения
`AUTH_SESSION_TTL_HOURS`.

```bash
curl -s http://localhost:5001/api/users                     # список (нужен админ)
curl -s 'http://localhost:5001/api/directory/search?q=смирнов'
curl -X POST http://localhost:5001/api/users      -H 'Content-Type: application/json'      -d '{"username":"j.smith","role":"user"}'
curl -X DELETE http://localhost:5001/api/users/j.smith      # отозвать
curl -X DELETE 'http://localhost:5001/api/users/j.smith?hard=true'   # удалить запись
```

> ⚠️ Пока список пуст, войти может только локальный админ — это защита от
> ситуации, когда весь домен получает доступ по умолчанию.

### OIDC (встроенный)

Authorization Code Flow с PKCE. На форме входа появляется кнопка рядом с полями
логина и пароля.

```bash
OIDC_ENABLED="true"
OIDC_ISSUER="https://sso.company.ru/realms/main"
OIDC_CLIENT_ID="mysql-ai-agent"
OIDC_CLIENT_SECRET="..."                  # пусто = публичный клиент, только PKCE
OIDC_REDIRECT_URL="https://monitor.company.ru/ai-agent/auth/oidc/callback"
OIDC_SCOPES="openid profile email"
OIDC_USERNAME_CLAIM="preferred_username"  # для Entra ID / Keycloak
OIDC_BUTTON_TEXT="Войти через SSO"
```

`OIDC_REDIRECT_URL` задавайте явно и ровно так, как он зарегистрирован у
провайдера: за nginx схему и хост автоматически не определить.

Как устроено: `/auth/oidc/login` уводит к провайдеру с `state` и PKCE-challenge,
`/auth/oidc/callback` меняет код на токены и берёт личность с **userinfo**.
Подпись ID-токена не проверяется — вместо этого userinfo запрашивается по TLS
напрямую у issuer с полученным access-токеном. Так не нужен разбор JWT и
работа с JWKS, а доверие опирается на TLS-соединение с провайдером. Если ваша
политика требует именно проверки подписи ID-токена — скажите, это отдельная
доработка.

`state` одноразовый (защита от CSRF), живёт 10 минут в памяти процесса. При
рестарте агента незавершённые входы придётся повторить.

Полученный логин проходит через список доступов на общих основаниях: нет
выданного доступа — редирект на форму с объяснением.

### Что остаётся открытым без входа

| Путь | Почему |
|------|--------|
| `/login`, `/api/login` | сама форма входа |
| `/health` | проверки `verify.sh` и мониторинга |
| `/static/*` | стили и скрипты формы |
| `/auth/oidc/login`, `/auth/oidc/callback` | иначе до входа не дойти — бесконечный редирект |
| `/webhook` | Alertmanager не умеет логиниться — вместо этого принимается **только с localhost**, с любого другого адреса 403 |

WebSocket `/ws` проверяет сессию отдельно: HTTP-middleware на него не
распространяется. При истёкшей сессии соединение закрывается кодом 4401 и
интерфейс просит войти заново.

### Отключить аутентификацию

`AUTH_ENABLED="false"` — интерфейс открыт всем, у кого есть сетевой доступ.
Допустимо только в изолированном сегменте.

Помимо встроенного OIDC остаётся вариант с oauth2-proxy перед nginx и
режимом SSO по заголовку — он не требует настройки провайдера в самом агенте.

## Диагностика проблем

**«Неверный логин или пароль», хотя пароль верный.** Спецсимволы в пароле
здесь ни при чём: форма отправляет его в JSON (`JSON.stringify`), оболочка его
не трогает, до `ldap3` он доходит байт в байт. Настоящих причин обычно три:
не тот формат имени для bind, состояние учётной записи (истёк пароль,
блокировка) или опечатка в DN группы.

Каталог всё это знает — Active Directory возвращает код в тексте ошибки
(`data 52e` и т. п.). Скрипт [scripts/ldap_test.py](scripts/ldap_test.py)
показывает его и перебирает формы имени:

```bash
sudo ./scripts/ldap_test.py --user ivkop
```

Он выведет состав пароля (длину и число спецсимволов, сам пароль не
показывается — видно, что он дошёл целиком), попробует UPN, `ДОМЕН\имя`,
имя без домена и полный DN из каталога, а затем проверит, существуют ли
указанные группы и входит ли в них пользователь. Если подходит не та форма,
что в `config.env`, скрипт прямо назовёт нужное значение
`LDAP_BIND_TEMPLATE`.

Коды AD, которые агент теперь расшифровывает в логе:

| код | причина |
|-----|---------|
| `525` | пользователь не найден |
| `52e` | неверный пароль |
| `530` | вход запрещён в это время суток |
| `531` | вход с этого компьютера запрещён |
| `532` | срок действия пароля истёк |
| `533` | учётная запись отключена |
| `701` | срок действия учётной записи истёк |
| `773` | требуется смена пароля |
| `775` | учётная запись заблокирована |

Частый случай после импорта из nslcd: `LDAP_BIND_TEMPLATE` собирается как
`{username}@домен` из `base DN`, но в домене реальный UPN-суффикс другой —
например, `base` содержит `DC=corp,DC=company,DC=ru`, а входят люди как
`ivkop@company.ru`. Bind тогда отклоняется с `data 52e`, и это неотличимо от
опечатки в пароле.

**`LDAP-аутентификация <имя> не прошла: required argument is not a integer`**
— исправлено в 1.16.3. Это не пароль и не права: ldap3 на Linux кладёт
`receive_timeout` в `pack('LL', ...)`, а `struct` не принимает дробное число.
`LDAP_TIMEOUT` читался через `float()`, поэтому bind обрывался ещё до
обращения к каталогу. На Windows та же ветка ldap3 делает `int(...)`, из-за
чего баг проявлялся только на сервере.

Теперь `LDAP_TIMEOUT` — целое число секунд. Дробное значение в `config.env`
округляется вниз, минимум 1 секунда. Лечится обновлением агента:

```bash
sudo ./scripts/install_agent.sh
```

Заодно в логе теперь видно, что именно произошло: `LDAP: неверный пароль или
имя` — это ошибка пользователя, а `LDAP-аутентификация ... (тип): ...` со
словами «сбой подключения или настройки» — повод смотреть `config.env`.

**`Не удалось выдать доступ`, в логе `near "ON": syntax error`** — исправлено
в 1.18.7. Запись доступа шла через UPSERT (`INSERT ... ON CONFLICT DO UPDATE`),
а он появился только в SQLite 3.24. В RHEL и CentOS 7 идёт 3.7, и для неё это
синтаксическая ошибка. Заменено на `INSERT OR IGNORE` плюс `UPDATE` — понимают
все версии, и при одновременной выдаче двум админам ничего не ломается.

Версия SQLite теперь пишется в лог при запуске:

```bash

**Бесконечный редирект на форму входа** — исправлено в 1.16.1. Причина:

**Ошибки разбора config.env, «$2: unbound variable», не проходит вход
локального администратора** — исправлено в 1.16.2. Причина: хеш пароля имеет
вид `pbkdf2_sha256$200000$соль$хеш`, а записывался в двойных кавычках. Файл
читается через `source`, то есть обычным bash, — и `$200000` со `$соль`
подставлялись как переменные. Под `set -u` установка обрывалась с ошибкой, без
него от хеша оставался огрызок `pbkdf2_sha25600000` и пароль не подходил. То же
касалось паролей с `$`, `` ` `` и `\`.

Теперь секреты пишутся в **одинарных** кавычках, а старые конфиги чинятся
на лету: значения перечитываются из файла напрямую, минуя подстановку

Пароль заново вводить не нужно — исходный хеш в `config.env` не пострадал.

```

Если видно `pbkdf2_sha25600000` — конфиг ещё старый, перезапустите установку.

**В Grafana дашборды пустые, хотя в Prometheus метрики есть**

Сначала убедитесь, что данные действительно собираются:
```bash
curl -s 'http://localhost:9090/api/v1/label/job/values' | python3 -m json.tool
# ожидаем: prometheus, mysql_<кластер>, node_<кластер>
```

Если job'ы на месте, а панели пустые — это несовпадение имён job. Community-дашборды
(1860, 7362 и другие) фильтруют по `job="node"` / `job="mysql"`, а `apply` генерирует
`job` вида `node_kemerovo` / `mysql_kemerovo`. Проверить:
```bash
curl -s 'http://localhost:9090/api/v1/query?query=up{job="node"}' \
  | python3 -c "import json,sys; print(len(json.load(sys.stdin)['data']['result']))"
# 0 -> дашборд ищет не тот job
```

Используйте дашборд **«MySQL кластеры — обзор»** (папка *MySQL AI Monitoring*) —
он лежит в [grafana/dashboards/](grafana/dashboards/) и написан под метки этого
проекта: селектор сверху переключает кластеры по метке `cluster`, в легендах
человеческие названия из `cluster_label` и роль primary/replica. Ставится
провижинингом, отдельного импорта не требует:
```bash
sudo ./scripts/install_monitoring.sh    # Prometheus/Grafana уже стоят — скрипт их пропустит
```

Community-дашборды при этом остаются: их можно донастроить, поправив переменную
`$job` вверху дашборда, либо просто не использовать.

**Панели пишут «Datasource not found» или `${DS_PROMETHEUS}`** — дашборд
импортирован без привязки датасорса. Перезалейте: `sudo ./scripts/install_monitoring.sh`.

**Grafana не стартует / `Grafana-Server Init Failed`** — быстрее всего снести
сгенерированные конфиги и создать заново:

```bash
sudo ./scripts/install_monitoring.sh --clean
```

Режим `--clean` останавливает Prometheus, Alertmanager и Grafana, удаляет
**только то, что создаёт этот скрипт** (`prometheus.yml`, правила,
`alertmanager.yml`, systemd-юниты, наш провижининг Grafana и дашборды из
`/var/lib/grafana/dashboards`) и раскладывает всё заново из `config.env`
и `clusters.json`.

Не трогаются: метрики в `/var/lib/prometheus`, `grafana.db` с пользователями
и вручную созданными дашбордами, `alerts.db` с алертами, чатами и доступами.

То же для всего стека сразу: `sudo ./scripts/install_all.sh --clean`.

**`Datasource provisioning error: data source not found`** — частный случай,
из-за которого Grafana падает на старте целиком. Возникает, если в `grafana.db`
уже есть датасорс «Prometheus» со случайным `uid` (его создал провижининг
прошлых версий, без явного uid), а новый файл задаёт `uid: prometheus`:
сопоставление идёт по uid, запись не находится, модуль провижининга падает.

Удаление файла провижининга **не помогает** — запись живёт в `grafana.db`.
Поэтому наш файл содержит блок `deleteDatasources`, который сносит старую
запись по имени перед созданием новой. Достаточно переустановить конфиги:

```bash
sudo ./scripts/install_monitoring.sh --clean
```

Если и после этого не стартует — причина не в наших файлах:

```bash
journalctl -u grafana-server -n 40 --no-pager | grep -A3 -i "init failed\|error"
ls -la /var/lib/grafana/          # права: должно быть grafana:grafana
df -h /var/lib/grafana            # место на диске
ss -tlnp | grep :3000             # порт не занят другим процессом
```

Ниже — частные случаи.

**`Grafana-Server Init Failed`** — Grafana не стартует, если провижининг-файл
невалиден, ссылается на несуществующий каталог или в этом каталоге лежит битый
JSON. Точная причина печатается сразу после `Init Failed:`:
```bash
journalctl -u grafana-server -n 40 --no-pager | grep -A3 -i "init failed\|error"
```
Быстро поднять, отключив провижининг дашбордов:
```bash
sudo mv /etc/grafana/provisioning/dashboards/mysql_monit.yml /tmp/
sudo systemctl restart grafana-server
```
`install_monitoring.sh` создаёт этот файл только после того, как в
`/var/lib/grafana/dashboards` лёг хотя бы один проверенный дашборд, поэтому
повторный прогон скрипта такую ситуацию не создаёт.

**Самопроверка не запускается сама при открытии вкладки** — так и задумано
с версии 2.8.1: она обходит все серверы по SSH и дёргает модель, и делать это
при каждом заходе на вкладку незачем. Нажмите «Проверить сейчас». По
расписанию проверка идёт своим чередом (`SELFCHECK_INTERVAL_MIN`), и
сломанный доступ приходит событием.

**После перезагрузки не видно, что ответ дописывается** — а он
дописывается: тот же вопрос, заданный повторно, отвечал мгновенно, потому
что работа была уже сделана. Причина — гонка: сокет открывается за
миллисекунды, а какой разговор текущий, известно только когда придёт ответ
на запрос истории. Просьба «подключи меня обратно» уходила первой, с пустым
разговором, и сервер её игнорировал. С 2.12.0 подключение вызывается из трёх
мест — открылся сокет, пришла история, сменили разговор, — и срабатывает то,
которое узнало последним.

**За сутки на графиках не видно, какой день** — подписи оси читались как
«03:00, 09:00, 15:00, 21:00, 03:00». Дата добавлялась по длине периода
(дольше 36 часов), а не по тому, меняется ли день. С 2.12.0 дата ставится у
первой отметки и у каждой, что начинает новый день, — и на экране, и в
печатном отчёте, где спросить «а это какой день» вообще не у кого.

**После долгого простоя страница пустая** — сессия кончилась, а вкладка
осталась открытой: запросы начинали отказывать, и человек видел пустой
интерфейс без объяснений. С 2.9.0 первый же отказ уводит на форму входа —
перехват стоит в одном месте, обёрткой вокруг `fetch`, поэтому ни один из
полусотни запросов не забыт. Закрытый сокет с кодом 4401 делает то же самое.

**Ответ в чате обрывался через 5 минут** — сторож в браузере отсчитывал время
от отправки вопроса, а не от последнего признака работы. С 2.8.1 отсчёт
сбрасывает любой пришедший токен или шаг сбора; пять минут теперь означают
пять минут **тишины**. Со стороны агента ожидание модели задаётся
`LLM_TIMEOUT` (300 с) — это тоже время до очередной порции ответа, а не на
весь ответ целиком.

**WebSocket рвётся за прокси** — увеличьте `proxy_read_timeout` (клиент шлёт
ping каждые 25с, таймаут должен быть больше).

**После добавления кластера он не появился** — забыли `sudo ./manage_cluster.sh apply`.

**Раздел пуст, а в блоке — `You have an error in your SQL syntax ... near
'reads'`** — псевдоним совпал с зарезервированным словом MySQL. `READS` —
характеристика хранимых процедур (`READS SQL DATA`), и без обратных кавычек
сервер отвечает 1064 на весь запрос. Симптом при этом безобидный: раздел
выглядит как «данных нет». Исправлено в 2.9.2, а `tests/test_agent.py` теперь
проверяет все псевдонимы в запросах агента по списку зарезервированных слов.

**`SHOW ENGINE INNODB STATUS` и тексты запросов обрывались на шестидесяти
символах** — форматтер резал каждую ячейку, чтобы таблица не разъезжалась.
Ровно то, ради чего раздел и открывают. С 2.9.2 колонка, которая не влезает
в таблицу (длиннее 90 символов **или** содержащая перевод строки), печатается
отдельным абзацем и целиком; остальные остаются выровненной таблицей.
Обрезается только совсем гигантское значение — с явной пометкой, сколько
символов осталось за кадром.

**Диагностика отвечала `504 Gateway Time-out`** — набор запросов по двум
серверам с планами выполнения идёт дольше, чем nginx готов ждать (минуту по
умолчанию), и на исходе прокси отдавал HTML-страницу вместо ответа. С 2.9.1
запросы набора выполняются параллельно (`DIAG_PARALLEL`, по умолчанию 4),
серверы опрашиваются разом, а ответ приходит раньше терпения прокси
(`DIAGNOSE_BUDGET_S`, 40 с):

> Набор ещё выполняется — на большой базе он занимает больше 40 с. Работа не
> прервана и идёт дальше: нажмите «Выполнить» ещё раз через полминуты, и
> готовый отчёт покажется сразу.

Работа при этом **не бросается**: она досчитывается в фоне и ложится в
память задач, поэтому повторное нажатие отдаёт готовое мгновенно. Если
хочется дождаться с первого раза — поднимите `proxy_read_timeout` в nginx и
`DIAGNOSE_BUDGET_S` в `config.env`.

**Раздел отвечает `TypeError: ... missing required arguments`** — у функции
поменялась сигнатура, а один из вызовов за ней не поехал. С 2.9.0 такое ловит
`tests/test_calls.py` до выкладки: он разбирает исходники, находит вызовы
функций самого агента и сверяет их с сигнатурами (проверок около восьмисот).

Он же ловит второй похожий случай — когда переменная затирает вложенную
функцию. Так сломался сбор метрик в чате: внутри `build_chat_context`
объявлена функция `step()`, а ниже по коду `step = parse_step_seconds(...)`,
и следующий её вызов упал с `'int' object is not callable`. Имена
разрешаются, сигнатуры сходятся, работает до первой такой строки.

**Метрик нет, хотя `curl` с того же сервера их отдаёт** — httpx берёт прокси
из окружения (на Windows ещё и из реестра), и запрос к собственному
Prometheus уходил наружу. С 2.9.0 к внутренним адресам агент ходит мимо
прокси: `http_client()` в `agent/services/prometheus.py`.

**Чтение лога упирается в таймаут** — с версии 2.8.0 большие файлы читаются
делением (см. «Логи в несколько гигабайт»). Если таймаут остался, поднимите
`LOG_READ_TIMEOUT` в `config.env` (по умолчанию 180 секунд) — на очень
медленных дисках даже суженный поиск может не уложиться.

## Безопасность

- `config.env` и `/opt/ai-alert-agent/.env` имеют права 600 (содержат токен LLM)
- `/clusters` API не отдаёт пароли exporter'ов наружу
- Агент работает от непривилегированного пользователя `aiagent`
- Пользователь MySQL `exporter` ограничен: только SELECT/PROCESS/REPLICATION CLIENT, max 3 соединения
- Веб-интерфейс не имеет аутентификации — размещайте за VPN или nginx с basic auth:
  ```nginx
  location / {
      auth_basic "DBA only";
      auth_basic_user_file /etc/nginx/.htpasswd;
      proxy_pass http://127.0.0.1:5001;
  }
  ```
